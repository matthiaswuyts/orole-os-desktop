# Build the agent VM with NixOS, behind an FHS mask

Orole should build its per-agent micro VM guest with **NixOS**, from a pinned flake in Linux CI, and ship it to Windows as a read-only kernel, initrd and erofs store image. The deciding factor is not boot time or image size, where neither distro clearly wins. It is that Nix gives Orole's Go control plane what it lacks today: content-addressed, diffable environments that `policy`, `audit_events`, bot configs, skills and session resume can all refer to exactly. NixOS has one real cost, and it is a large one. Agents' default habits (`pip install`, `npx playwright install`, vendor install scripts, `#!/bin/bash`) assume a Debian-shaped filesystem, and that is where most of the reported trouble with "agents on Nix" comes from. So the guest has to present that shape by default, using `nix-ld`, `envfs` and a broad library set, and agents should never author the system configuration. The claim that agents are worse at Nix is **partly true and mostly irrelevant to this design**. No benchmark compares agent success on NixOS with Debian. The only Nix-specific benchmark shows frontier models failing about 15–35% of small, deliberately tricky NixOS repair tasks. In Orole's design, Orole writes the Nix and agents only consume it. The recommendation is conditional. Phase 2 should run a one-week compatibility spike with explicit pass criteria. If the FHS layer cannot make the agents' everyday installs work, fall back to a Debian base with a Nix store layer on top, which keeps most of the control-plane benefits.

## Size and boot speed are a wash, and neither has been measured head to head

Debian sets a clear, documented baseline. The current Debian 13 `genericcloud` amd64 image is **219 MB as tar.xz and 326 MB as qcow2**, with a 3.0 GB sparse raw disk ([cloud.debian.org](https://cloud.debian.org/images/cloud/trixie/latest/)). NixOS has no official slim image, and a careless build is clearly larger. A January 2026 Discourse report found a switchable image with a **1.3 GB store** "even with many things disabled". That report compressed to about 340 MB and listed the kernel (165 MB), Python (116 MB) and Perl (63 MB) as the largest paths ([NixOS Discourse](https://discourse.nixos.org/t/how-minimal-can-a-nixos-image-get/45268)). The same thread puts a trimmed headless system at 200–400 MB, and shows that about 500 MB of the minimal ISO is `linux-firmware`, which a VM does not need. The upstream `perlless` profile goes further. It fails the build if anything references Perl, disables in-place switching and turns off docs ([nixpkgs commit](https://code.ornl.gov/nix/nixpkgs/-/commit/91103e7d7c7efe349834c44abf5d6f3e7496e4d7)). Booting the kernel and initrd directly also removes grub and firmware entirely. A tuned NixOS base is therefore plausibly as small as Debian's or smaller, but that is an estimate, not a measurement. More importantly, the base hardly matters. Chromium, Python and Node add several hundred megabytes on either distro, and **no published source measures either distro with that payload**. The real size lever on both is the layout the earlier sandbox report already proposed: one read-only base image shared by every VM, plus a small per-agent qcow2 overlay.

Boot time is in the same position. The only NixOS microVM numbers come from a 2023 microvm.nix tuning commit under QEMU. A no-op VM went from **10.2 s to 4.8 s**, and most of the remainder was unexplained serial-device waits in the initrd, not Nix-specific work ([microvm.nix log](https://code.querie.cc/mirrors/microvm.nix/log/nixos-modules/microvm/optimization.nix?showmsg=1)). Depot's Debian/Ubuntu-style microVMs measured **about 3.6 s, dominated by cloud-init** ([Depot](https://depot.dev/blog/optimizing-microvm-boot-times)). Each distro has one distinctive cost. For Debian it is cloud-init, which a custom image omits. For NixOS it is the activation script, historically written in Perl. nixpkgs is replacing it with a systemd initrd, `nixos-init` and userborn, explicitly so that startup can run in parallel ([nixpkgs nixos-init](https://git.gay/transgirllucy/nixpkgs/src/branch/nixos-25.11/pkgs/by-name/ni/nixos-init)). With both tuned, the userspace difference is probably under a second. QEMU on WHPX and Chromium startup will dominate "agent ready" time. So the answer to "is NixOS larger or slower to boot?" is: **only when built carelessly, and nobody has published a fair comparison**. The Phase 2 spike should measure both images under `-accel whpx` with direct kernel boot and an identical service set, rather than treat any figure above as settled.

## The case that agents are worse at Nix rests on thin, mixed evidence

The skeptical reading holds up better than the folklore. **No published benchmark compares the same agent tasks on NixOS and on an apt-based system.** Terminal-Bench 2.0, the main terminal-agent benchmark, packages each of its 89 tasks in a Docker image and reports no per-distro breakdown ([arXiv 2601.11868](https://arxiv.org/abs/2601.11868v1)). The only Nix-specific harness is NixBench. It is a single-author, non-peer-reviewed GitHub project that gives agents broken Nix repositories whose defects appear only at runtime, with prompts that describe symptoms rather than causes. Its corpus 2.0 run in June 2026, with one run per row, put the best models at **22/26 (85%)**. Claude Code with Opus 4.8 scored 19–21/26, and GPT-5.6 variants scored 66–76% on a 29-task set. Raising effort did not improve scores consistently, and three tasks (`container-native-vs-oci`, `debug-network-false-lead`, `issue-report-quality`) defeated every top baseline ([NixBench results](https://github.com/maximilianpw/nixbench/blob/main/docs/runs/2026-06-24-model-comparison.md)). The current 3.2.0 corpus, which includes Opus 5.5, is explicitly labelled calibration evidence with results still pending ([NixBench README](https://github.com/maximilianpw/nixbench)). Those numbers show that authoring subtle NixOS module semantics (systemd escaping, networking, container modes) is still error-prone. They say nothing about whether an agent doing ordinary coding work is worse off on a NixOS box than on Debian, because there is no Debian control group.

The most-cited anecdote is weaker than its reputation. Claude Code issue #7954 claimed Opus's Nix output was "most often wrong and hallucinated". In the thread itself, Opus accepted a Codex review that was wrong (it claimed `cargo-tarpaulin` is not packaged, but it is) and later retracted. The reporter then closed the issue in November 2025 as no longer happening ([claude-code#7954](https://github.com/anthropics/claude-code/issues/7954)). Positive anecdotes are just as uncontrolled. Michael Stapelberg reports that a Claude skill generating microvm.nix VM definitions "always got the VM creation correct" ([Stapelberg](https://michael.stapelberg.ch/posts/2026-02-01-coding-agent-microvm-nix/)). Birkey describes an agent using `nix develop` to obtain a Rust toolchain while leaving the host untouched ([Birkey](https://www.birkey.co/2026-03-22-why-i-love-nixos.html)).

What the evidence does support is narrower and more useful. The failures people report cluster into two groups. The first is hallucinated attribute paths and options: "a single wrong attribute path cascades into a broken build" ([Vaughan](https://codex.danielvaughan.com/2026/05/30/codex-cli-nix-development-mcp-nixos-flakes-reproducible-agent-environments/)). The second, more common, is the agent's environmental reflexes failing. Prebuilt binaries expect `/lib64/ld-linux-x86-64.so.2`, the Claude Code installer's own binary will not run on NixOS ([claude-nixos](https://github.com/ducks/claude-nixos)), pip wheels with C extensions break ([NixOS Wiki](https://nixos.wiki/wiki/Python)), and `playwright install` fails outright ([NixOS Wiki: Playwright](https://wiki.nixos.org/wiki/Playwright)). Neither group is about reasoning. The first is a lookup problem, and the second is a filesystem-layout problem, and both have established fixes. mcp-nixos exists specifically so assistants "shouldn't hallucinate about packages", at a cost of about 1,030 tokens of context ([mcp-nixos](https://github.com/utensils/mcp-nixos)). `nix-ld` puts a shim at the standard loader path so pip, npm and vendor binaries run unpatched ([nix-ld](https://github.com/nix-community/nix-ld)). **No one has measured how much either fix closes the gap**, so that remains open. The fair verdict is this. Agents are measurably fallible at *writing* tricky Nix. They are plausibly worse at *improvising installs* on a bare NixOS box, though nobody has measured it. Nothing shows they are worse at coding inside a well-prepared Nix environment.

## Debian wins the everyday-compatibility fight outright

That compatibility tax is the honest core of the case for Debian, and it lands exactly on Orole's workload. An agent with a shell and a browser will run `pip install`, `npm install`, `npx playwright install` and vendor install scripts, and on Debian every one of those works. On NixOS each needs a workaround, and some workarounds are fragile. nixpkgs Python ignores `NIX_LD_LIBRARY_PATH`, so native wheels need RPATH rewriting tools such as fix-python ([crescentro.se](https://crescentro.se/posts/python-nixos/)). Playwright needs nixpkgs `playwright-driver.browsers`, plus `PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS`, plus an npm version that exactly matches the nixpkgs build. Users report "Executable doesn't exist" errors when they drift apart ([Discourse](https://discourse.nixos.org/t/synchronize-versions-of-playwright-driver-browsers-and-npm-package/66267)). The prior report's plan to use "the distro or Playwright Chromium" therefore needs a version-coupling decision on NixOS that it does not need on Debian. Third-party skills that ship `#!/bin/bash` scripts break, because NixOS keeps only `/bin/sh` and `/usr/bin/env` ([CodeCrafters forum](https://forum.codecrafters.io/t/shebangs-suppose-fhs-compliant-system/9473)). The most telling evidence comes from a Nix-native project. Nous Research's Hermes Agent ships a hardened NixOS mode in which the agent "cannot install new packages at runtime". It also ships a persistent **Ubuntu** container mode, recommended for "agents that need self-modification" ([Hermes docs](https://hermes-agent.nousresearch.com/docs/getting-started/nix-setup)). Even Nix enthusiasts keep an apt escape hatch.

Orole's own code adds smaller, concrete frictions. The SSH host-memory probe hard-codes `/bin/hostname`, `/bin/uname` and `/bin/cat`, none of which exist on NixOS ([host_memory.go](../internal/machines/host_memory.go)). `cliruntime` deliberately tracks each vendor's *latest* release within 30 minutes ([runtime.go](../internal/cliruntime/runtime.go)), while nixpkgs lags vendors and its `claude-code` wrapper disables auto-update ([nixpkgs package.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/by-name/cl/claude-code/package.nix)). Orole would therefore have to maintain its own overlay that bumps versions and hashes. That is the data `cliruntime` already fetches, but it adds a CI job. Codex is the easy case, since its Linux asset is a statically linked musl binary ([spec.go](../internal/cliruntime/spec.go)). Claude and Grok are most likely glibc-dynamic and need `nix-ld` or `autoPatchelf`, though the notes did not verify this. Most of the existing Linux code paths do work unchanged: the terminal backend uses only `/bin/sh` and `/usr/bin/env` ([backend_linux.go](../internal/terminals/backend_linux.go); [tmux_linux.go](../internal/terminals/tmux_linux.go)).

Build tooling is neutral. Nix does not run natively on Windows, so the image must be built in WSL2 or Linux CI and shipped prebuilt ([NLnet libnix](https://nlnet.nl/project/libnix/)). Debian's `debootstrap` and `mkosi` need a Linux build host too ([Arch Wiki: mkosi](https://wiki.archlinux.org/title/Mkosi)). Reproducibility is not neutral. Pinning a Debian build means relying on snapshot.debian.org, whose throttling was bad enough that the Qubes team built its own snapshot service ([Qubes forum](https://forum.qubes-os.org/t/reproducible-builds-for-debian-a-big-step-forward/6800)). A Nix image, by contrast, is fully specified by `flake.lock`, and its standard packages come from cache.nixos.org rather than being compiled.

## Nix pays off in Orole's control plane, not inside the VM

The strongest arguments for NixOS appear when its properties are mapped onto Orole's existing seams. Today bots declare capabilities but no software environment. `BotConfig` has tools, MCP server ids, skills and access levels, but no package or runtime field ([api.go](../internal/chat/api.go)). Code tasks can only choose among harnesses *installed on the host* ([bot_tasks.go](../internal/daemon/bot_tasks.go)). A new `BotConfig.Environment` list would be validated like `Skills`. It maps one-to-one onto a Nix `buildEnv` pinned to a nixpkgs revision. On Debian the same list becomes an `apt install` whose result depends on mirror state on the day it runs.

The same precision helps approvals. `policy.Request` already carries a dotted action and a resource string ([policy.go](../internal/policy/policy.go)). A request such as `sandbox.env.add` on `nixpkgs/<rev>/ffmpeg` can show "+N store paths, +M MB" and be remembered as an exact rule. `execute.go` already refuses PATH lookups so that an approval binds to an exact executable ([execute.go](../internal/machines/execute.go)). A `/nix/store/<hash>-claude-code-X/bin/claude` path binds to exact *content*, while `/usr/bin/claude` binds only to a location that can change underneath it.

Skills gain explicit dependencies. Today the frontmatter parser reads only `name` and `description` ([frontmatter.go](../internal/skills/frontmatter.go)). A `packages:` key would let a skill's helper scripts get their interpreter through `nix shell` instead of whatever the image happens to contain. Sessions gain reproducible resume. Nothing currently records the harness version on a `Session` ([types.go](../internal/agents/types.go)). Recording the guest profile generation next to `AgentSessionID` and `BaseRef` means a resumed CLI runs the same binary that wrote the transcript. Rolling back a bad package addition then becomes a profile switch ([Nix manual](https://nix.dev/manual/nix/2.28/command-ref/nix-env/rollback)) rather than discarding an overlay along with the work in it. Egress is narrower too. In the NIC-less design, on-demand packages come through the daemon proxy from one signed cache host instead of PyPI, npm and arbitrary GitHub release URLs. This narrows legitimate egress but does not replace the egress allowlist as the real control point. Finally, Orole currently detects no `flake.nix`, `shell.nix`, devenv or devcontainer files at all ([projects.go](../internal/projects/projects.go)). A Nix guest could launch a harness inside a project's own `nix develop` shell. That flake is repo-controlled code, though, so evaluating it must be a policy-gated action under Orole's rule that repo content is untrusted ([AGENTS.md](../AGENTS.md)).

One much-advertised NixOS advantage mostly disappears on Orole's host. The microvm.nix pattern that Stapelberg, nixbox and Keystone use shares the *host's* `/nix/store` into every VM over virtiofs or 9p ([microvm.nix shares](https://microvm-nix.github.io/microvm.nix/shares.html); [nixbox](https://github.com/razvanz/nixbox)). A Windows host has no `/nix/store`. virtiofsd is Linux-only, and QEMU's 9p-on-Windows work shows no activity since 2022 ([QEMU #974](https://gitlab.com/qemu-project/qemu/-/issues/974)). The workable design is a block device. Attach one erofs store image, built in CI, read-only to every VM, with a qcow2 overlay per VM. Debian can do exactly the same with a read-only rootfs image. Deduplication across *per-agent additions* still favours Nix, because content-addressed paths are identical across agents, whereas per-agent `apt install`s are duplicated in each overlay. The base-layer sharing itself is a tie. microvm.nix is therefore useful to Orole as a source of guest modules and image outputs (kernel, initrd, erofs store), not as a VM runner: its host side assumes systemd, tap and virtiofsd, and has no stated WHPX support ([microvm.nix](https://github.com/microvm-nix/microvm.nix)).

| Question | NixOS guest | Debian-slim guest |
|---|---|---|
| Base image size | Unofficial; 200–400 MB compressed when trimmed, 1.3 GB store if careless | 219 MB tar.xz / 326 MB qcow2 (genericcloud) |
| Boot to userspace | No fair benchmark; 4.8 s untuned microVM (2023) | No fair benchmark; ~3.6 s with cloud-init |
| Agent `pip`/`npm`/vendor binaries | Need `nix-ld`, `envfs`, wheel fixes | Work as-is |
| Playwright | Pinned `playwright-driver.browsers`, version-coupled | `playwright install` works |
| Image reproducibility | Fully specified by `flake.lock` | Depends on snapshot.debian.org or own mirror |
| Per-bot environments, approvals, resume | Content-addressed, diffable, exact rules | Mutable package names, overlay-only rollback |
| Windows build host | WSL2 or Linux CI | WSL2 or Linux CI |
| Shared base across VMs on Windows | Read-only erofs block image | Read-only rootfs block image |

## How to take advantage of NixOS without inheriting its tax

The design that captures the benefits keeps Nix authoring on Orole's side and presents agents with a normal Linux. Orole maintains a `guest/` flake in the repo, built in GitHub Actions and never on the user's machine. It produces a kernel, an initrd and an erofs store containing the Go guest agent, Xvfb or `cage`, Chromium, Python, Node, git, `bubblewrap` and `socat` (which Claude Code's Linux sandbox wants ([nixpkgs package.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/by-name/cl/claude-code/package.nix))), plus an Orole overlay that pins the harness CLIs at the versions and hashes `cliruntime` already resolves.

The system enables `programs.nix-ld` with a broad library set (glib, nss, X11, mesa) and `envfs`, so that `/bin/bash`, `/usr/bin/python3`-style shebangs and downloaded ELF binaries resolve. It ships `uv` so agents get FHS-style Python instead of fighting nixpkgs Python. It uses direct kernel boot, the systemd initrd, `nixos-init` with userborn, the perlless profile where Chromium's closure allows, and no docs or firmware. One rule matters here. Do not apply overrides that cause cache misses on Chromium: they turn a cached download into a multi-hour rebuild ([rix binary-cache vignette](https://docs.ropensci.org/rix/articles/binary-cache.html)).

Inside the VM, the agent gets a writable home and a writable per-user Nix profile on the overlay. It also gets a system-prompt line saying the box is NixOS, that `nix shell nixpkgs#x -c` and `uv` are the install paths, and that `apt` and `nix-env` do not exist. Optionally the gateway also serves mcp-nixos so attribute names are looked up rather than guessed. Agents never run `nixos-rebuild`. Direct kernel boot makes NixOS system generations moot anyway, so per-user profiles are the useful unit of rollback.

In the daemon, the new pieces are `BotConfig.Environment`, a `sandbox.env.*` policy vocabulary, a sandbox table holding closure diffs (because `audit_events.detail` truncates at 300 characters ([policy.go](../internal/policy/policy.go))), the profile generation and harness store path recorded on each session, and a guest-side build-time version check instead of `cliruntime` running `--version` on the host.

The Phase 2 spike should state its pass criteria before it starts. On the stock image, with no hand-holding, each of the following should run: the Claude Code native installer, `pip install numpy pandas` and a wheel with C extensions, `npm install` with a native module, `npx playwright install chromium` followed by a test, `mise install node`, and a sample of third-party skills with bash scripts. Measure boot-to-agent-ready and idle RAM against a Debian-slim image under WHPX. Run a small A/B of real Orole code tasks on both guests, which would also supply the head-to-head data the field is missing. If the FHS layer clears the list, ship NixOS. If it does not, ship Debian as the base and install Nix inside it as a read-only `/nix/store` layer plus per-bot profiles. That hybrid keeps content-addressed environments, exact approvals and reproducible resume, while giving up the declarative base image and clean image reproducibility.

## Conclusion

The NixOS-versus-Debian question turns out to be two questions. One is what agents should see, and the answer there is plainly an ordinary FHS Linux, because agents' install habits are trained on it and Debian provides it for free. The other is what Orole should manage, and the answer there is plainly Nix, because Orole's policy, audit, bot and resume machinery all improve when an environment is a hash rather than a history of `apt` calls. NixOS with `nix-ld` and `envfs` is a bet that one system can satisfy both, and the evidence that it can is real but anecdotal. That is why the recommendation comes with a measurable exit rather than as a conviction.

The "agents are bad at Nix" debate also has an underrated consequence. Orole could produce the first honest data on the question. Running the same code tasks on a Nix guest and a Debian guest, with and without mcp-nixos grounding, is cheap once both images exist. No public benchmark has done it, and the result would settle Orole's choice on evidence rather than folklore.
