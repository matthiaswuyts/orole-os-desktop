# Windows-native virtualization options for per-agent local VMs (state as of 15 Oct 2026)

Scope: every way a per-user Windows 10/11 desktop app written in Go (no admin at runtime if possible) can create, start, snapshot and destroy small VMs locally, with an own filesystem, terminal and browser per AI agent. The developer machine is **Windows 11 Pro build 22000 (21H2)**, so features needing a newer build are flagged with **[needs >22000]**. Dates of sources are given where they matter; anything pre-2025 is labelled "older".

---

## 1. Hyper-V Host Compute Service (HCS) / hcsshim / computestorage: can a non-admin create VMs, what did Microsoft build on it, Go libraries, group requirements?

### Takeaway
HCS (computecore.dll) is the real "create a lightweight VM from JSON" API on Windows and supports save/restore and clone-from-template, but Microsoft documents that **only Administrators or members of the local "Hyper-V Administrators" group may use it**. Every Microsoft product built on it (WSL2, WSL containers, Windows Sandbox, Hyper-V isolated containers/LCOW) and third parties (Docker, Podman, Claude Cowork) therefore either run a privileged broker service or require a one-time elevated step that adds the user to Hyper-V Administrators.

### Cited Findings
- **What HCS is:** "The Host Compute System API provides the functionality to start and control VMs and containers." Supported operations are create/start/stop for VMs and containers, plus "pause, resume, save and restore" for VMs; the API can also start and interact with processes inside the compute system. Compute systems are ephemeral: once stopped, the app must create a new one. The client must pre-create the VHD, configure networking (HCN) and create Hyper-V sockets before calling HCS; configuration is a JSON document. Applies to Windows 10 October 2018 Update (1809), Server 2019/2022. — [HCS overview, Microsoft Learn](https://learn.microsoft.com/en-us/virtualization/api/hcs/overview)
- `HcsCreateComputeSystem` takes a JSON document that must contain one of `Container`, `VirtualMachine` or `HostedSystem`; its `securityDescriptor` parameter "is reserved for future use and must be NULL" (so you cannot ACL a compute system to a user at creation). — [HcsCreateComputeSystem reference](https://learn.microsoft.com/virtualization/api/hcs/reference/HcsCreateComputeSystem)
- **Privilege requirement (authoritative):** `HCS_E_ACCESS_DENIED` (0x8037011B): "Insufficient privileges. Only administrators or users that are members of the Hyper-V Administrators user group are permitted to access virtual machines or containers. To add yourself to the Hyper-V Administrators user group, please see https://aka.ms/hcsadmin". Other relevant codes: `HCS_E_HYPERV_NOT_INSTALLED` (0x80370102) and `HCS_E_SERVICE_NOT_AVAILABLE` (0x80370114) "a required feature is not installed". — [HCS error codes](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hcshresult)
- **Snapshot / clone primitives in the HCS schema:** `SaveOptions.SaveType` = `"ToFile"` ("memory and device states are saved to the runtime state file") or `"AsTemplate"` ("placed in a state such that other systems can be cloned from it"); `RestoreState.SaveStateFilePath` and `RestoreState.TemplateSystemId` ("The ID of the template system to clone this new system off of"); `GuestState.ForceTransientState` uses state files "as templates to populate transient, in-memory state". Also `Plan9` shares (`Name`, `AccessName`, `Path`, `Port`, `AllowedFiles`), `VirtualSmb` shares, and `HvSocketSystemConfig` (see Q8). — [HCS schema reference](https://learn.microsoft.com/en-us/virtualization/api/hcs/schemareference)
- **hcsshim (Go):** "the Golang interface for using the Windows Host Compute Service (HCS)", also contains a Host Network Service (HNS) interface (`hcn/`), `computestorage/`, `ext4`, `vsockexec`, and the Linux guest agent ("commonly referred to as the GCS or Guest Compute Service", built with `GOOS=linux ./cmd/gcs`) "to support running Linux Hyper-V containers". "Primarily used in the Moby and Containerd projects." The `containerd-shim-lcow-v2` (LCOW, Linux utility VM) requires "Windows Server 2025 (build 26100) or later". Privilege requirements are not stated in the README. — [microsoft/hcsshim](https://github.com/microsoft/hcsshim)
- LCOW v1 vs v2 (older): in v2 "the utility VM is a first-class object that can be managed in a lifetime separate from the actual containers"; an old vendored runhcs comment says the utility VM defaults to 2 vCPUs and "the platform default is 1024MB" memory (older, may be stale). — [opengcs on pkg.go.dev](https://pkg.go.dev/github.com/Microsoft/opengcs); [Moby commit mirror](https://git.coopcloud.tech/p4u1/docker-cli/commit/553c4b8a9bced90eb6f751f4615b114fb142ab9b)
- **WSL is built on HCS through a privileged service:** "Client processes call into wslservice.exe, which is a privileged Windows service. That service has the capability to create virtual machines (via HCS)". For WSL containers (WSLC), wslservice.exe "does not retain ownership of the virtual machine. Instead, it creates a child process, wslcsession.exe, which runs on behalf of the calling user" — giving "strong isolation between sessions, since they live in different processes". — [WSLC architecture deep dive, Windows Command Line blog, 29 Sep 2026](https://devblogs.microsoft.com/commandline/?p=11811)
- **Windows Sandbox** "benefits from new container technology in Windows" (dynamic base image, direct-map memory sharing, host-reclaimable memory). — [Windows Sandbox architecture](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-architecture)
- **Hyper-V isolated containers:** "Each container runs inside of a highly optimized virtual machine and effectively gets its own kernel." — [Nested virtualization doc](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/nested-virtualization)
- **Podman's experience (third-party precedent):** operating Hyper-V machines needs two privileged operations: creating/deleting Hyper-V sockets and managing VMs; "starting and stopping VMs is only possible from an elevated process unless the user is a member of the Hyper-V administrators group". Podman 6 added `podman system hyperv-prep` (run once, elevated) which "creat[es] the required registry entries in HKEY_LOCAL_MACHINE for Hyper-V VSock communication" (one VSock entry per mounted host folder, default 2, entries persist after machines are removed) and adds the current user to Hyper-V Administrators, to "avoid the need for administrator privileges during normal machine operations". — [podman-system-hyperv-prep(1)](https://docs.podman.io/en/latest/markdown/podman-system-hyperv-prep.1.html); [Podman blog](https://blog.podman.io/?p=21919); [podman PR #27650](https://github.com/containers/podman/pull/27650)
- docker-machine issue (older): members of "Hyper-V Administrators" can create and destroy VMs; the tool wrongly required full admin. — [docker/machine#2989](https://github.com/docker/machine/issues/2989)
- Hyper-V Administrators membership gives "complete and unrestricted access to all features of Hyper-V" without making the account an administrator (vendor documentation, not Microsoft). — [IBM docs](https://www.ibm.com/support/knowledgecenter/SSMKFH/com.ibm.apmaas.doc/install/hyperv_config_add_nonadmin_user_hyperv_usergroup.html); older guidance says Hyper-V has no RBAC without SCVMM — [Thomas Marcussen blog](https://blog.thomasmarcussen.com/allowing-non-administrators-to-control-hyper-v/)
- **Claude Cowork (desktop agent VM) uses HCS on Windows** and hits the privilege wall: user report "HCS operation failed: failed to create compute system: HcsWaitForOperationResult failed with HRESULT 0x80070005" (Mar 2026, closed as not planned). — [anthropics/claude-code#39285](https://github.com/anthropics/claude-code/issues/39285). Community reports say Cowork runs a `CoworkVMService`, that the MSIX package needed the restricted capability `rescap:Capability Name="hypervisor"`, and that Windows Home "includes vmcompute (used by WSL2) but not vmms or vmplatformapi.dll", so Cowork requires Pro/Enterprise (community claims, not Anthropic docs). — [claudeissues #46417](https://claudeissues.com/issue/46417-bug-cowork-msix-manifest-missing-hypervisor-capability-coworkvmservice-cannot-ac); [claudeissues #27906](https://claudeissues.com/issue/27906-docs-cowork-requirements-should-clearly-state-windows-pro-enterprise-is-required)

### Inferences
- A per-user Go daemon cannot call HCS directly with a standard token. Options: (a) one-time elevated install step adds the user to **Hyper-V Administrators** (Podman 6 pattern; requires sign-out/sign-in for the token to pick up the group); (b) ship a **SYSTEM service broker** that owns HCS calls and exposes a narrow, authenticated named-pipe API to the per-user daemon (WSL/WSLC/Cowork pattern). Option (b) conflicts with Orole's "no admin at runtime" only at install time, but adds a privileged component that becomes part of the security boundary.
- Hyper-V Administrators is a powerful group (full control of all VMs and their disks); granting it to the interactive user widens the blast radius of any compromise of that user. This is a judgment from the documented scope of the group, not a cited Microsoft statement.
- HCS gives everything needed for a per-agent microVM design: direct kernel boot of a Linux utility VM (as LCOW/WSL do), Plan9/VirtualSmb shares, HvSocket with per-VM SDDL, save-to-file, and clone-from-template (`AsTemplate` + `TemplateSystemId`) for fast "fork from warm template" starts. It is the only Windows-native API documented here with first-class save/restore/clone.
- Go access: `github.com/Microsoft/hcsshim` (internal packages wrap HCS; public surface is container-oriented and many VM helpers live under `internal/`, so a project would likely vendor or call computecore.dll via `golang.org/x/sys/windows` directly). This is an inference from the repo layout; not verified API-by-API.
- Because WSL2 runs on Windows Home via vmcompute (community claim above), HCS itself appears present on Home with the Virtual Machine Platform feature, but Hyper-V Manager/VMMS is not. Not confirmed by Microsoft docs.

### Gaps
- No Microsoft doc found that states whether HCS on Home (VMP only) accepts third-party `HcsCreateComputeSystem` calls for Linux VMs, or which HCS schema features require the full Hyper-V role.
- No published measurements found for HCS utility-VM (LCOW/Krypton) boot time or minimum memory in 2025-2026; only the old 1024 MB default.
- "Krypton" naming and Docker Desktop's exact use of HCS were not confirmed from primary sources this session.
- Exact Go API surface of hcsshim for raw VM creation (outside containerd shims) not verified.

## 2. Windows Hypervisor Platform (WHP/WHPX): what user-mode VMMs can do, Home availability, QEMU+WHPX quality in 2025-2026

### Takeaway
WHP (WinHvPlatform.dll, since Windows 10 1803) is a KVM-like user-mode API: the calling process owns guest memory and runs vCPUs in its own threads, so a VMM (QEMU, OpenVMM, Hyperlight, VirtualBox NEM) runs as an ordinary process with no service or group. The feature is enableable on Home, but enabling it needs admin + reboot. QEMU+WHPX works for Linux guests on x86_64 and (since 2025) arm64, but has documented MMIO/legacy-device performance caveats; there are no 2026 benchmarks.

### Cited Findings
- "This API is available starting in the Windows April 2018 Update." Functions exported by `WinHvPlatform.dll` (header `WinHvPlatform.h` in the Windows SDK): `WHvCreatePartition`/`WHvSetupPartition`/`WHvDeletePartition`, `WHvMapGpaRange` ("sets a region in the caller's process as the backing memory"; memory allocated with `VirtualAlloc` or mapped files), `WHvMapGpaRange2` (map memory "in a specified host process"), `WHvQueryGpaRangeDirtyBitmap`, `WHvRunVirtualProcessor` (blocking per-vCPU thread loop with exit contexts for MMIO, I/O port, MSR, CPUID), optional hypervisor-emulated local APIC, SynIC messages, notification ports, triggers, `WHvResetPartition`, partition migration functions, and VPCI device assignment. Page updated 11 Jun 2026; Arm64 support detected via `WHvCapabilityCodeFeatures`/`Arm64Support`. — [WHP API definitions](https://learn.microsoft.com/en-us/virtualization/api/hypervisor-platform/hypervisor-platform)
- **QEMU WHPX (current master docs):** works on x86_64 and arm64; built on `Vid`, "which uses the same hypercalls as Linux's mshv driver". x86_64 tested from Windows 10 2004; arm64 needs "Windows 11 24H2 with the April 2025 optional updates or May 2025 security updates". Enable via `DISM /online /Enable-Feature /FeatureName:HypervisorPlatform /All`. Limitations: guests using MMX/SSE/AVX for MMIO unsupported; legacy VGA "performance will be quite suboptimal"; legacy PIC interrupts don't wake HLT with the Hyper-V interrupt controller (disabled by default on Windows 10; use `-M q35,pic=off` + UEFI); `kernel-irqchip` is debug-only; arm64 lacks SVE/SME. `-accel whpx,ssd=off` gives "a significant MMIO performance increase" at the cost of BTB-flush mitigations. Example: `qemu-system-x86_64.exe -accel whpx -M pc -smp cores=2 -m 2G ...`. — [QEMU WHPX docs](https://www.qemu.org/docs/master/system/whpx.html)
- QEMU 11.0 adds WHPX support for the arm64 `virt` board; Mohamed Mediouni's "whpx: add arm64 support"/"interrupt controller support" series reached v12 (28 patches) in late Dec 2025. — [linuxiac QEMU 11.0](https://linuxiac.com/qemu-11-0-released-with-dropped-32-bit-host-support/); [patch series tracker](https://ci.syzbot.org/series/461ea8f4-1829-4850-881b-507398453137)
- Older WHPX issues: `-smp` topology presented incorrectly to Linux guests (QEMU 7.0 bug); "WHPX: Unexpected VP exit code 4" crashes unless VMX is disabled on the vCPU; a user found Linux under WHPX "decent" but `-cpu host` crashed. — [QEMU issue 1137](https://gitlab.com/qemu-project/qemu/-/issues/1137); [SerenityOS WSL notes](https://git.rgbcu.be/RGBCube/serenity/src/commit/bc9f8f5c39e5d36fda2cd06da242cfbddae1bebe/Documentation/NotesOnWSL.md); [Whonix forum](https://forums.whonix.org/t/proof-of-concept-whonix-on-qemu-on-windows/22606)
- **VirtualBox on Hyper-V (NEM via WHP):** the "green turtle" icon means VirtualBox runs in a degraded mode because Hyper-V/VBS owns VT-x, "significantly" reducing performance; a VirtualBox 7.2.10 guest hung at boot on Windows 11 with VBS/HVCI active in NEM mode. — [Kicksecure wiki](https://www.kicksecure.com/wiki/VirtualBox/Green_Turtle_Issue); [Whonix forum 2026](https://forums.whonix.org/t/whonix-vms-gateway-workstation-hang-at-black-screen-during-boot-under-virtualbox-7-2-10-on-windows-11-with-active-vbs-hvci-nem-mode/23292)
- **OpenVMM** (Microsoft, Rust) runs as a "conventional hosted, or 'type-2' Virtual Machine Monitor" as a single `openvmm.exe`; Windows x64/Aarch64 hosts use WHP; boot modes UEFI, PCAT BIOS, Linux Direct Boot; devices virtio-fs, virtio-9p, virtio-net, virtio-pmem, VMBus storvsp/netvsp, NVMe, vTPM; "management interfaces continue to evolve". Development is "currently focused on its role in the OpenHCL paravisor". — [OpenVMM guide](https://openvmm.dev/guide/user_guide/openvmm.html); [microsoft/OpenVMM](https://github.com/microsoft/OpenVMM)
- **Home edition:** a Windows 11 Home 25H2 user had both "Virtual Machine Platform" and "Windows Hypervisor Platform" enabled while `Microsoft-Hyper-V` was "unknown" on Home. A Microsoft Q&A community answer claims VMP is unavailable on Home (contradicted by the former). — [claudeissues #33492](https://claudeissues.com/issue/33492-bug); [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/a/6983167)
- QEMU+WHPX in Azure VMs is not supported even with nested virtualization. — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/a/2017844)

### Inferences
- WHP is the only Windows-native path where the VMM is a plain per-user process with no privileged broker: once `HypervisorPlatform` is enabled, the Orole daemon could spawn `qemu-system-x86_64.exe -accel whpx` or `openvmm.exe` per agent, under the user's token, inside a Job Object. This is the strongest fit for "no admin at runtime". (That WHP calls need no elevation is widely relied on by QEMU/Hyperlight users but I did not find an official Microsoft statement; see Gaps.)
- WHP provides no snapshot API beyond reset/migration primitives and a dirty bitmap; snapshots are the VMM's job (QEMU savevm/qcow2 snapshots; Hyperlight `snapshot()`/`restore()`).
- For a browser-capable Linux guest, QEMU+WHPX with virtio devices and `-M q35,pic=off` + UEFI (or OpenVMM direct boot) avoids the slow legacy paths the QEMU docs warn about.

### Gaps
- No official doc found stating WHP calls require no admin/no group (only that enabling the feature uses DISM).
- No 2025-2026 benchmarks (boot time, CPU/IO overhead) for QEMU+WHPX Linux guests; no OpenVMM-on-Windows boot numbers.
- Cloud Hypervisor has no WHP backend that I could confirm; libkrun Windows/WHP backend status unverified.
- Whether WHP on Windows 11 21H2 (22000) supports all APIs QEMU 10/11 use (e.g., `WHvMapGpaRange2`, newer state APIs) is unverified.

## 3. Microsoft Hyperlight (micro-VMs on WHP/KVM/MSHV): capabilities, limits, maturity, fit for terminal/browser

### Takeaway
Hyperlight is an embeddable Rust VMM library for running functions in micro-VMs that have **no OS kernel, no syscalls, no filesystem and no network** by default, with millisecond creation and microsecond calls. It is pre-1.0 and cannot run a terminal or browser; Hyperlight-Nanvix (Jan 2026) adds a POSIX microkernel for language runtimes (Python/JS) but is still aimed at ephemeral serverless code, not interactive desktops.

### Cited Findings
- "Hyperlight is a lightweight Virtual Machine Manager (VMM) designed to be embedded within applications." "No kernel or OS in the VM. Guests are regular ELF binaries written in `no_std` Rust or C"; "Guests are sandboxed by default with no access to the host filesystem, network, etc."; by default guests can only print to the host; host and guest "communicate through typed function calls"; `snapshot()`/`restore()` reset VM memory between calls; supports "KVM, MSHV, and Windows Hypervisor Platform"; sandboxes "spin up in milliseconds, with guest function calls completing in microseconds"; explicitly not designed for "Running full-blown Linux guest workloads that need syscalls, networking, or filesystem access"; "Hyperlight is pre-1.0. The API may change between releases"; CNCF sandbox project (~4.7k stars). Related: hyperlight-wasm, hyperlight-js, hyperlight-unikraft ("runs Linux applications (Python, Node.js, Go, Rust, C/C++) using Unikraft as the guest kernel"). — [hyperlight-dev/hyperlight](https://github.com/hyperlight-dev/hyperlight); [README](https://cdn.jsdelivr.net/gh/hyperlight-dev/hyperlight@main/README.md)
- **Windows prerequisites (current):** "Requires Windows 11 Pro/Enterprise/Education or Windows Server 2025 or later", with Windows Hypervisor Platform enabled ("requires a reboot"); WSL2 can be used as a Linux/KVM host. — [Hyperlight getting started](https://github.com/hyperlight-dev/hyperlight/blob/main/docs/getting-started.md). Older (2024-25) guidance said "Windows 11 / Windows Server 2022 or later". — [Zenn article (older)](https://zenn.dev/zenogawa/articles/hyperlight-wasm)
- Original announcement claim (Nov 2024, older): ~1-2 ms to create a VM. — [Winaero](https://winaero.com/microsoft-introduces-the-open-source-hyperlight-hypervisor-project); CNCF sandbox acceptance Feb 2025 — [desdelinux](https://blog.desdelinux.net/en/Hyperlight-is-an-open-source-project-from-Microsoft-that-integrates-into-apps-that-run-isolated-or-untrusted-code./)
- **Hyperlight Nanvix (28 Jan 2026):** Nanvix is "a Rust-based microkernel created by the Systems Research Group at Microsoft Research", "not a general-purpose OS—it's a minimal OS tailored specifically for ephemeral serverless workloads"; "provides over 150 POSIX system calls, enabling support for Python, JavaScript, WASI, Rust, and C/C++ applications without code changes"; "double-digit millisecond-order cold starts" including runtime load; "hundreds of instances per GiB of memory"; three deployment modes (single process, multi-process, disaggregated two-VM). Windows/WHP support not mentioned. — [Microsoft Open Source blog](https://opensource.microsoft.com/blog/2026/1/28/github.com/hyperlight-dev/hyperlight-nanvix)
- **MXC (Microsoft eXecution Containers)** exposes `hyperlight` and `microvm` (Nanvix) backends on Windows 11 x64/ARM64, both marked experimental, alongside `processcontainer` (default), `windows_sandbox`, `wslc` and `isolation_session`; SDKs in Rust, .NET and Node. — [microsoft/mxc](https://github.com/microsoft/mxc). InfoWorld (3 Sep 2026) calls MXC "still a very young project" (0.8.0 preview) and notes "MXC cannot provide more isolation than you get from a locked-down virtual environment". — [InfoWorld](https://www.infoworld.com/article/4215416/running-ai-agents-in-sandboxes-with-microsoft-execution-containers.html). Third-party sources disagree on MXC GA (one claims GA with SDK 1.0.0 on 7 Oct 2026; unverified). — [byteiota](https://byteiota.com/microsoft-execution-containers-mxc-ai-agent-sandbox/)

### Inferences
- Hyperlight/Nanvix fit a "run this tool call / code snippet" sandbox (Python, JS) embedded in a host process, not "each agent gets a VM with a shell and Chromium". No fork/exec-heavy shells, no GPU/display, no network stack inside the guest.
- Hyperlight is a Rust library; a Go daemon would need a Rust sidecar process or C FFI. Its Windows build floor now names Pro editions and Server 2025, which suggests it relies on newer WHP features; whether it runs on 22000 is unknown.

### Gaps
- No Hyperlight GitHub release version/date retrievable this session (releases list empty in capture); no 2026 benchmark numbers for Hyperlight-on-WHP.
- Whether Hyperlight Nanvix runs on Windows/WHP is not stated.
- Exact Windows build that Hyperlight requires on Pro (21H2 vs 22H2+) not confirmed.

## 4. Windows Sandbox: programmatic control, instance limit, startup, editions, minimum build

### Takeaway
Windows Sandbox is a disposable Windows (not Linux) VM on Pro/Enterprise/Education. Since Windows 11 24H2 it has a `wsb` CLI (start/list/exec/share/stop/connect/ip), but `exec` returns only an exit code (no stdout), user-context exec needs an RDP-style `connect`, and Microsoft's docs (updated 8 Oct 2026) still say **only one instance can run at a time**, so it cannot give each agent its own VM.

### Cited Findings
- **CLI, "Starting with Windows 11, version 24H2"** [needs >22000]: common `--raw` (JSON output). `wsb start [--id <id>] [-c|--config "<Configuration>...</Configuration>"]` returns a sandbox ID; `wsb list` shows the current user's sessions (ID, status running/stopped, uptime); `wsb exec --id <id> -c <command> -r <ExistingLogin|System> [-d <dir>]` "returns the exit code" and "Currently, there is no support for process I/O meaning that there is no way to retrieve the output of a command"; "An active user session is required to execute a command in the context of the currently logged on user ... This can be done using the connect command"; `wsb share --id <id> -f <host-path> -s <sandbox-path> [-w|--allow-write]`; `wsb connect --id <id>` opens a remote desktop window; `wsb ip --id <id>`; `wsb stop --id <id>`. — [Windows Sandbox CLI](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-cli)
- **Single instance (still, Oct 2026):** "Windows Sandbox currently doesn't allow multiple instances to run simultaneously." Editions: Pro, Enterprise, Pro Education/SE, Education; "currently not supported on Windows Home edition". Network on by default (disable via config). "Starting with Windows 11, version 22H2, data persists through restarts initiated within the sandbox" [needs >22000]. "Takes a few seconds to launch, supports virtual GPU". Page updated 2026-10-08. — [Windows Sandbox overview](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)
- **Footprint:** dynamic base image is "a compressed 30-MB package" and "occupies about 500 MB of disk space" once installed; "direct map" shares host physical pages for OS binaries (e.g., `ntdll.dll`); host can reclaim sandbox memory "much like it would with a process"; GPU virtualization needs WDDM 2.5+, else WARP CPU rendering. — [Windows Sandbox architecture](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-architecture)
- Older prerequisites (2018 preview post): ≥4 GB RAM (8 GB recommended), ≥2 cores. A custom FLARE-VM based sandbox reported ~10 s startup (not stock). — [Windows Kernel Internals blog (older)](https://techcommunity.microsoft.com/t5/windows-kernel-internals-blog/windows-sandbox/ba-p/301849); [dsebastien](https://www.dsebastien.net/windows-sandbox/)
- `.wsb` configuration XML (networking, mapped folders, logon command, etc.) is the same format accepted by `wsb start --config`. — [Windows Sandbox configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file); [CLI doc](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-cli)
- MXC lists `windows_sandbox` as an experimental Windows backend; InfoWorld describes it as configurable "with managed, read-only access to selected host folders" and suggests a "shadow" agent in Windows Sandbox. — [microsoft/mxc](https://github.com/microsoft/mxc); [InfoWorld](https://www.infoworld.com/article/4215416/running-ai-agents-in-sandboxes-with-microsoft-execution-containers.html)
- Related but not a VM: Windows 11 **Agent Workspace** (preview from late 2025) runs agents in "a separate Windows session" under their own agent account; Microsoft calls it "more efficient than a full virtual machine such as Windows Sandbox"; enabling it requires an administrator and applies to all users. — [TechRadar](https://www.techradar.com/computing/windows/microsoft-explains-how-windows-11s-ai-agents-will-work-as-testing-is-about-to-start-and-ill-admit-im-nervous); [Windows Latest](https://windowslatest.com/2025/11/18/windows-11-to-add-an-ai-agent-that-runs-in-background-with-access-to-personal-folders-warns-of-security-risk)

### Inferences
- On the developer's 21H2 build, only `.wsb` files launched via `WindowsSandbox.exe` are available (no CLI, no in-sandbox restart persistence). Even on 24H2, one-instance-only rules it out for "one VM per agent"; it could serve as a single shared "Windows browser/desktop" sandbox, with output returned via a shared folder because `exec` has no stdout.
- A Windows guest gives Edge out of the box but no Linux terminal; agent tooling would need to be installed on each launch (pristine every time) via a logon command from a read-only mapped folder.

### Gaps
- No rigorous measured boot time or RAM figure for stock Windows Sandbox in 2025-2026 found.
- Whether `wsb` CLI ships to 23H2 via Store/servicing is not documented; docs say 24H2.

## 5. WSL2: shared utility VM, per-agent distros, APIs, nested KVM, memory, networking, hvsocket, open source, and the new WSL containers (WSLC)

### Takeaway
Classic WSL2 runs **all distros in one shared utility VM per user** (one kernel, one memory budget, one `wsl --shutdown`), so per-agent distros are namespace isolation, not VM isolation. The big 2026 change is **WSL containers (WSLC)**: GA on 29 Sep 2026 in WSL 3.0.1, with a C/C#/C++ SDK whose *sessions* each get their own VHD and (per a hands-on test) their own VM, owned by a per-user `wslcsession.exe`, with Consommé user-mode networking and virtiofs. WSLC is the closest Microsoft-supported "per-app lightweight Linux VM API" in 2026, but installing WSL still needs admin + reboot once.

### Cited Findings
- **Shared VM:** `.wslconfig` configures "the virtual machine powering WSL 2 (RAM, kernel to boot, number of CPUs, etc.)" for all distros; `wsl --shutdown` "Immediately terminates all running distributions and the WSL 2 lightweight utility virtual machine". `isolateDistroCgroup` (default `true`) "Enables per-distribution cgroup isolation". — [WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config); [WSL basic commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- **Per-agent distro lifecycle commands:** `wsl --import <Name> <InstallLocation> <FileName> [--vhd] [--version 1|2]` (file may be `-` for stdin); `wsl --import-in-place <Name> <file.vhdx>` (ext4); `wsl --export <Name> <FileName> [--vhd]` ("Exports a snapshot ... Defaults to tar format"); `wsl --unregister <Name>` (data permanently lost); `wsl --terminate <Name>`; `wsl --install [--no-launch] [--web-download] [--location]`; `wsl --mount <Disk> [--vhd] [--bare] [--name] [--type] [--options]`. — [WSL basic commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- **`.wsl` tar distros (WSL ≥ 2.4.4):** root FS tar (gzip recommended) + `/etc/wsl-distribution.conf` (`[oobe] command/defaultUid/defaultName`, `[shortcut]`, `[windowsterminal]`); install with `wsl --install --from-file <file>`; `--name` overrides default name; enterprise manifests via `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Lxss\DistributionListUrl` (admin); "The archive should not contain a kernel or an initramfs". — [Build a custom distro](https://learn.microsoft.com/en-us/windows/wsl/build-custom-distro)
- **wslapi.dll:** `WslRegisterDistribution`, `WslUnregisterDistribution`, `WslLaunch`, `WslLaunchInteractive`, `WslConfigureDistribution`, `WslGetDistributionConfiguration`, `WslIsDistributionRegistered` (2019-era API). — [wslapi.h](https://learn.microsoft.com/en-us/windows/win32/api/wslapi/)
- **WSL plugin API:** lets an app "specify a Windows executable that starts when the WSL virtual machine is started", which "can create Linux processes inside of WSL, and ... communicate directly to them using a virtualized socket"; installed via `HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Lxss\Plugins` (admin); "WSL plugins will only run if they are digitally signed"; code "runs in the same address space as the WSL service"; `ExecuteBinary()` processes run "in the root namespace of the WSL2 Virtual Machine ... not associated to any distribution", a tmpfs "Mariner based root file system". — [WSL plugins](https://learn.microsoft.com/en-us/windows/wsl/wsl-plugins)
- **`.wslconfig` [wsl2] facts (doc updated 16 Sep 2026):** `memory` default 50% of host RAM; `processors` default all; `swap` default 25% of RAM; `nestedVirtualization` default `true` (¹ Windows 11 only); `vmIdleTimeout` 60000 ms (¹); `networkingMode` default `NAT`, values `none`, `nat`, `bridged` (deprecated since 2.4.5), `mirrored`, `consomme` (formerly `virtioproxy`; NAT falls back to Consommé since 2.3.25) (¹² **Windows 11 22H2+**); `firewall` and `dnsTunneling` default `true` (¹²); `localhostForwarding` default `true`; `defaultVhdSize` 1 TB; `virtiofs` experimental (default false); `kernel`, `kernelModules`, `kernelCommandLine`, `loadKernelModules`, `systemDistro`. `[general] instanceIdleTimeout` 15000 ms. `[experimental] autoMemoryReclaim` default `dropCache` (values `disabled`/`gradual`/`dropCache`), `sparseVhd` default false, `hostAddressLoopback` (mirrored only, ¹²). Footnotes: ¹ "Only available on Windows 11", ² "Require Windows 11 version 22H2 or higher". — [WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
- **Memory reclaim (older, 2019):** freed Linux memory is returned and `vmmem` shrinks; page cache keeps vmmem high (example: ~2 GB on Windows vs ~50 MB used in Linux) unless dropped. — [WSL memory reclaim blog (older)](https://devblogs.microsoft.com/commandline/memory-reclaim-in-the-windows-subsystem-for-linux-2/)
- **Nested KVM inside WSL2:** the 6.18 WSL kernel builds `CONFIG_KVM=m`, `CONFIG_KVM_INTEL=m`, `CONFIG_KVM_AMD=m`, so no custom kernel is needed; with `nestedVirtualization=true` ("the default on Windows 11") `/dev/kvm` appears after `wsl --shutdown`; x86 only (ARM64 WSL boots at EL1, KVM needs EL2). (3 Jun 2026) — [boxofcables](https://www.boxofcables.dev/build-a-custom-wsl-2-kernel-in-2026/)
- **Windows 10 regression:** in "lifted" (Store/open-source) WSL, nested virtualization is "unconditionally disabled on Windows 10" ("The check is on the Windows major version, not on the underlying CPU"), made explicit in commit 6f47fa9b (6 Jan 2026); reported on WSL 2.8.11.17 / kernel 6.18.26.3-1 (7 Jun 2026); labelled bug, open, PR #41914 open. — [microsoft/WSL#40735](https://github.com/microsoft/WSL/issues/40735)
- **Host CPU/OS floor for nesting:** Intel VT-x+EPT: Windows 10+/Server 2016+; "AMD EPYC / Ryzen processor or later: The Hyper-V host must be either Windows Server 2022 or later, or Windows 11 or later" (so 22000 qualifies). — [Enable nested virtualization](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/enable-nested-virtualization)
- **WSL open source:** majority released 19 May 2025 (announced at Build, 20 May 2025): wsl.exe, wslg.exe, wslservice.exe, Linux-side networking/port-forwarding daemons; still closed: Lxcore.sys (WSL1), P9rdr.sys and p9np.dll (9P redirection). — [Wikipedia](https://en.wikipedia.org/wiki/Windows_Subsystem_for_Linux); [heise](https://heise.de/-10390292); [Linux Hint](https://linuxhint.com/windows-subsystem-linux-open-source/)
- **WSLC timeline:** announced at Build (2 Jun 2026) — [heise, 3 Jun 2026](https://heise.de/-11317626); public preview 29 Jun 2026; GA 29 Sep 2026 ("now generally available for anyone who runs wsl --update"; WSL 3.0.1; Craig Loewen: "ready for use for full development and production use cases"). — [It's FOSS](https://itsfoss.com/news/wslc-general-availability/); [Windows Latest, 1 Oct 2026](https://www.windowslatest.com/2026/10/01/microsofts-then-ceo-called-linux-a-cancer-and-now-windows-11-ships-linux-containers-with-upgraded-wsl/); [SmartScope, checked 11 Oct 2026](https://smartscope.blog/en/blog/wsl-containers-public-preview-2026/)
- **WSLC SDK:** C header `wslcsdk.h` / `wslcsdk.lib` / `wslcsdk.dll`; C# `Microsoft.WSL.Containers`; C++ `Microsoft::WSL::Containers`; layered "Session → Container → Process"; session settings for CPU count, memory, timeout, VHD, feature flags, termination callbacks; container settings for networking mode, port mappings, volumes, named volumes, init process, I/O callbacks; process API with stdin/stdout handles, signals, exit codes; image pull/import/load/tag/push; session VHD volumes; install/version helpers ("get missing components", "install with dependencies"); no snapshot/checkpoint API listed. — [WSL container API reference](https://wsl.dev/api-reference/)
- NuGet `Microsoft.WSL.Containers`: 2.9.3 (26 Jun 2026), 2.9.9 (25 Aug 2026), 3.0.1 (29 Sep 2026), **3.0.3 (13 Oct 2026)**; MIT; x64 and ARM64; target `net8.0-windows10.0.19041`; native package too. — [NuGet](https://www.nuget.org/packages/Microsoft.WSL.Containers)
- **WSLC architecture:** each session has its own VHD storing images, containers, networks, volumes (wslc.exe stores them in `%AppData%\Local\wslc\sessions`); Windows paths shared via virtiofs ("Compared to plan9, virtiofs is about twice as fast"), VHD-backed volumes with size caps (`wslc volume create --driver vhd -o SizeBytes=...`); **Consommé** networking: guest Ethernet frames go over a virtio queue to "a Windows process running as the user" that does DNS, TCP/UDP routing and port mapping, so traffic "flows as it was emitted by a regular Windows process". The post does not explicitly say one VM per session. — [WSLC architecture deep dive](https://devblogs.microsoft.com/commandline/?p=11811)
- **WSLC hands-on measurements (ComputingForGeeks, 1 Oct 2026; Windows 11 build 26100.9457 running *nested on Proxmox*, WSL 3.0.1, kernel 6.18.40.1-1, so absolute times are inflated):** each session is "its own VM with its own disk" (Task Manager shows `vmmemwslc-cli-admin-victor`, named per user and elevation); `storage.vhdx` 716 MB after pulling Ubuntu, `swap.vhdx` 36 MB; first `wslc run` 132.9 s (new VM + format + pull), repeat 2.81 s; cold start to first container exit median **34.1 s** (Docker-in-WSL 44.9 s); next container with VM running 5.9 s; idle nginx guest memory 341 MB, VM working set **706 MB**; session gets ~half host RAM by default; ports published on **127.0.0.1 by default**; virtiofs vs 9P sequential read 143 MB/s vs 17 MB/s; no `compose`, no Docker API shim; install required elevated `dism` enabling VirtualMachinePlatform + Microsoft-Windows-Subsystem-Linux, reboot, then ~350 MB MSI into `C:\Program Files\WSL`. — [ComputingForGeeks](https://computingforgeeks.com/?p=172378)
- WSLC requires WSL ≥ 2.9.3; GA adds Intune controls to enable/disable WSLC and registry allowlists; Defender for Endpoint plugin surfaces container activity. — [SmartScope](https://smartscope.blog/en/blog/wsl-containers-public-preview-2026/); [xenospectrum, 29 Sep 2026](https://xenospectrum.com/en/wsl-containers-ga-architecture-docker-boundaries/)
- AllThings.how (4 Jun 2026) reports Microsoft's framing that "each Windows application that uses the API gets its own lightweight virtual machine", with separate storage, networking and hypervisor-level isolation. — [AllThings.how](https://allthings.how/wsl-containers-how-windows-runs-linux-containers-with-wslc/)

### Inferences
- **Classic WSL2 per-agent distros** give cheap filesystem separation (`wsl --import` from a golden `.wsl`/tar or `--import-in-place` of a cloned VHDX in seconds) but share one kernel, one memory cap, one network namespace/IP in NAT mode, and one `wsl --shutdown`; a kernel exploit or root in one distro reaches all. Treat as "container-grade" isolation.
- **WSLC sessions are the best Windows-native fit for "one Linux VM per agent"** if the per-session-VM observation holds: create one WSLC session per agent (own VHD, own VM, CPU/memory caps), run a base image with a shell + headless Chromium, drive processes through the SDK's stdin/stdout handles (no ports), and use `wslcsession.exe` running as the user. Go can call `wslcsdk.dll` via `syscall`/`x/sys/windows` (C ABI) without cgo. Startup on bare metal should be well under the 34 s nested figure, but no bare-metal number exists yet.
- WSLC has no snapshot API; "snapshot" would be copying/cloning the session `storage.vhdx` while stopped, or committing a container image.
- For the 21H2 dev box: NAT and nested KVM work; mirrored/Consommé networking for classic WSL, `firewall`, `dnsTunneling` need 22H2+. WSLC's minimum Windows build is undocumented (NuGet target implies Windows 10 19041+ API surface).
- Running Orole's agents inside WSL does not by itself open network listeners if `localhostForwarding=false` (global setting) and no ports are published; WSLC publishes to 127.0.0.1 only when asked.

### Gaps
- Microsoft's own text confirming "one VM per WSLC session" was not found; it rests on a third-party test plus secondary reporting.
- WSLC minimum Windows build / edition (Home?) and whether the Store WSL 3.x supports Windows 11 21H2 are undocumented in what I found.
- No 2025-2026 measured cold-boot time or idle RAM for the classic WSL2 utility VM on bare metal.
- How a non-WSL host process obtains the WSL VM's GUID for AF_HYPERV without admin (`hcsdiag list` needs admin) is undocumented; the plugin API is the supported route but requires HKLM + code signing.

## 6. Firecracker / Cloud Hypervisor inside WSL2 via nested KVM: who does it, reliability on 22000 vs 22H2/24H2, performance

### Takeaway
It technically works when `/dev/kvm` exists in WSL2 (default on Windows 11 x86, including AMD on 22000), but it is unsupported by both Microsoft ("Non-Microsoft virtualization on Hyper-V virtualization isn't supported") and Firecracker ("nested virtualization is outside Firecracker's scope"), and I found no 2025-2026 production users or published performance numbers for Firecracker/Cloud Hypervisor inside WSL2.

### Cited Findings
- Microsoft: "Virtualization applications other than Hyper-V aren't supported in Hyper-V virtual machines, and are likely to fail." "Non-Microsoft virtualization on Hyper-V virtualization isn't supported." Running WSL2 in a nested Hyper-V VM is supported. — [What is nested virtualization](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/nested-virtualization)
- Firecracker needs read/write `/dev/kvm` (`[ -r /dev/kvm ] && [ -w /dev/kvm ]`). — [Firecracker getting started (fork mirror)](https://github.com/roypat/firecracker/blob/main/docs/getting-started.md). A maintainer said nested virtualization is outside Firecracker's scope and pointed to Cloud Hypervisor or QEMU; one commenter got it working with a custom kernel. — [firecracker#1721](https://github.com/firecracker-microvm/firecracker/issues/1721). A New Stack tutorial warns Firecracker "is not well tested under nested virtualization". — [The New Stack](https://thenewstack.io/tutorial-getting-started-with-firecracker-on-vmware-fusion/)
- A tutorial (Tutorials Dojo) uses WSL2 on Windows 10/11 and checks `ls /dev/kvm`, falling back to a full Linux VM if absent. — [Tutorials Dojo](https://tutorialsdojo.com/firecracker-for-students-launch-your-first-microvm-on-any-os/)
- Crabbox (agent sandbox tool): KVM/Firecracker in a Linux guest works "only when all outer layers expose the required virtualization extensions"; "generic nested KVM ... is not yet represented as one guaranteed provider feature"; its Firecracker provider targets a direct Linux KVM host. — [Crabbox nested execution](https://crabbox.sh/features/nested-execution.html)
- WSL kernel 6.18 ships KVM modules; nested is default on Windows 11; x86 only. — [boxofcables, Jun 2026](https://www.boxofcables.dev/build-a-custom-wsl-2-kernel-in-2026/). Older (2021-2022): needed a custom KVM-enabled WSL kernel; guide listed "Windows 11, build 22000+" and both Intel and AMD. — [boxofcables 2022 (older)](https://boxofcables.dev/kvm-optimized-custom-kernel-wsl2-2022); [Accelerated KVM guests on WSL 2 (older)](https://boxofcables.dev/accelerated-kvm-guests-on-wsl-2/)
- Windows 10 hosts: nested disabled in lifted WSL regardless of `.wslconfig` (open bug, Jun 2026); on Windows 10 enabling perfmon PMU/LBR with nesting caused partition-creation failure 0xC0350005. — [microsoft/WSL#40735](https://github.com/microsoft/WSL/issues/40735)
- AMD nested requires Windows 11 / Server 2022 host. — [Enable nested virtualization](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/enable-nested-virtualization)
- Hyperlight's own docs treat WSL2 as a valid KVM host for development. — [Hyperlight getting started](https://github.com/hyperlight-dev/hyperlight/blob/main/docs/getting-started.md)

### Inferences
- On 22000 (Windows 11), nested KVM in WSL2 should be available on both Intel and AMD (the Windows 11 gate is satisfied); no evidence that 22H2/24H2 changed nested behaviour, but no evidence of testing on 21H2 with current WSL 3.x either.
- Architecture cost: all Firecracker/CH microVMs would live inside the single WSL utility VM (shared memory cap = 50% host RAM by default, one point of failure on `wsl --shutdown`), with two-level nesting overhead on exits/MMIO, and host<->L2 traffic needs relaying via the L1 (Firecracker vsock is exposed in L1 Linux, then WSL→host via hvsocket/plugin). Snapshotting (Firecracker snapshot/restore) would work inside L1.
- Compared with QEMU/OpenVMM directly on WHP (one level, per-user process), nested KVM adds a layer and an unsupported configuration without improving isolation from the host.

### Gaps
- No credible 2025-2026 report of Firecracker or Cloud Hypervisor running reliably inside WSL2, and no boot-time/throughput numbers.
- No information on whether WSLC session VMs expose nested virtualization.

## 7. Licensing / edition constraints and the install-time story for a per-user (NSIS) installer

### Takeaway
Hyper-V (VMMS/Manager) and Windows Sandbox need Pro/Enterprise/Education; Virtual Machine Platform (WSL2/vmcompute) and Windows Hypervisor Platform can be enabled on Home. Every option requires a **one-time elevated step** (DISM feature enable + reboot, and for HCS also Hyper-V Administrators membership or a privileged service; for hvsocket listeners an HKLM registry entry). A per-user NSIS installer cannot do this silently; it must launch one UAC-elevated helper (or instruct the user) and then everything else can run per-user.

### Cited Findings
- Windows Sandbox editions: Pro, Enterprise, Pro Education/SE, Education; "not supported on Windows Home edition". — [Windows Sandbox overview](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)
- Hyper-V features are only in Pro, Enterprise, Education ("Home users will not see that option"); on Home 25H2, `Microsoft-Hyper-V` is "unknown" while VMP and WHP enable. — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/a/6983167); [claudeissues #33492](https://claudeissues.com/issue/33492-bug)
- Hyperlight on Windows lists "Windows 11 Pro/Enterprise/Education or Windows Server 2025 or later" and enabling WHP "requires a reboot". — [Hyperlight getting started](https://github.com/hyperlight-dev/hyperlight/blob/main/docs/getting-started.md)
- QEMU: enable WHP with `DISM /online /Enable-Feature /FeatureName:HypervisorPlatform /All` (Windows Features on client SKUs). — [QEMU WHPX docs](https://www.qemu.org/docs/master/system/whpx.html)
- WSL on a fresh image: `wsl --install --no-distribution`/`wsl --update` failed ("not installed", inbox stub); working path was elevated `dism` enabling `VirtualMachinePlatform` and `Microsoft-Windows-Subsystem-Linux`, reboot, then silent ~350 MB MSI to `C:\Program Files\WSL`. — [ComputingForGeeks, Oct 2026](https://computingforgeeks.com/?p=172378). `wsl --install` options: `--inbox`, `--enable-wsl1`, `--no-distribution`. — [WSL basic commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- HCS access requires Administrators or Hyper-V Administrators. — [HCS error codes](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hcshresult)
- Podman 6 pattern: one elevated `podman system hyperv-prep` (HKLM VSock entries + Hyper-V Administrators), then non-elevated operation; `--status` works unelevated; `--reset` undoes it. — [podman docs](https://docs.podman.io/en/latest/markdown/podman-system-hyperv-prep.1.html)
- Hyper-V socket service registration under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Virtualization\GuestCommunicationServices` "must be run as administrator". — [Make your own integration services](https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/user-guide/make-integration-service)
- WSL plugins: HKLM registration + Authenticode signing required. — [WSL plugins](https://learn.microsoft.com/en-us/windows/wsl/wsl-plugins)
- Claude Cowork (desktop app precedent): community reports that its MSIX needed the `hypervisor` restricted capability and that Home is unsupported because vmms is missing. — [claudeissues #46417](https://claudeissues.com/issue/46417-bug-cowork-msix-manifest-missing-hypervisor-capability-coworkvmservice-cannot-ac); [claudeissues #27906](https://claudeissues.com/issue/27906-docs-cowork-requirements-should-clearly-state-windows-pro-enterprise-is-required)
- Enterprises can disable WSLC via Intune. — [SmartScope](https://smartscope.blog/en/blog/wsl-containers-public-preview-2026/)
- VBS/HVCI and the Microsoft hypervisor force third-party hypervisors (VirtualBox) onto the slow WHP/NEM path. — [Kicksecure wiki](https://www.kicksecure.com/wiki/VirtualBox/Green_Turtle_Issue)

### Inferences
- Minimum-privilege path per option:
  - **QEMU/OpenVMM on WHP:** one elevated `DISM ... HypervisorPlatform` + reboot; then fully per-user. Works on Home and Pro.
  - **WSL2/WSLC:** one elevated enable of VMP (+WSL component) + reboot + WSL MSI/Store install (machine-wide); then per-user `wsl --import` / WSLC sessions. Works on Home and Pro.
  - **Direct HCS:** VMP/Hyper-V features + adding user to Hyper-V Administrators (re-logon) or installing a SYSTEM broker service; practical edition is Pro+ (Cowork precedent).
  - **Windows Sandbox:** elevated enable of `Containers-DisposableClientVM` (feature name from prior knowledge; not re-verified this session) + reboot; Pro+ only; CLI needs 24H2.
- A per-user NSIS installer can detect state without admin (e.g., `WHvGetCapability(WHvCapabilityCodeHypervisorPresent)`, `wsl --version`, `wsl --status`) and show a setup screen that launches a single elevated helper — consistent with Orole's "unconfigured integration = setup screen" rule.
- Windows 11 21H2 Home/Pro left mainstream servicing in Oct 2023 (prior knowledge, not re-verified this session); new WSL/WSLC/QEMU features are tested on 22H2+/24H2, so the 22000 dev box is a weak proxy for users.

### Gaps
- No Microsoft statement on whether the Store/MSI WSL 3.x (and thus WSLC) supports 21H2 (22000).
- Exact optional-feature names/requirements for Windows Sandbox on 24H2+ not re-verified.

## 8. Host<->guest channels without TCP listeners on network interfaces: hvsocket (AF_HYPERV), vsock, named pipes, 9p/Plan9, virtiofs

### Takeaway
Hyper-V sockets are the native, network-free channel (AF_HYPERV on Windows, AF_VSOCK in Linux guests; data "stays on the same physical memory"), available to Go via `github.com/Microsoft/go-winio` and `linuxkit/virtsock`. The catch: a **host-side listener** needs either an admin-registered service GUID in HKLM or an HCS VM whose JSON grants the user an SDDL; host-*connects*-to-guest-listener avoids registration. For files, WSLC uses virtiofs (~2x Plan9; measured 143 vs 17 MB/s sequential read), classic WSL uses 9P, HCS offers Plan9/VirtualSmb shares, and OpenVMM supports virtio-fs/9p.

### Cited Findings
- "All communication over Hyper-V sockets runs without using networking and all data stays on the same physical memory." Host: Windows 10+/Server 2016+; Linux guests need `CONFIG_VSOCKET=y`, `CONFIG_HYPERV_VSOCKETS=y`. "Data stream only". Service registration: "In order to use Hyper-V sockets, the application must be registered with the Hyper-V Host's registry" at `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Virtualization\GuestCommunicationServices\<GUID>` (ElementName), "This must be run as administrator". Linux VSOCK template GUID `00000000-facb-11e6-bd58-64006a7986d3` with the port in the first field (e.g., `00000ac9` = port 2761). Windows `socket(AF_HYPERV, SOCK_STREAM, HV_PROTOCOL_RAW)`, `SOCKADDR_HV{Family, Reserved, VmId, ServiceId}`; Linux `socket(AF_VSOCK, SOCK_STREAM, 0)`. VMID wildcards: `HV_GUID_ZERO/WILDCARD` 00000000-..., `HV_GUID_CHILDREN` 90db8b89-0d35-4f79-8ce9-49ea0ac8b7cd, `HV_GUID_LOOPBACK` e0e16197-dd56-4a10-9195-5ee7a155a838, `HV_GUID_PARENT` a42e7cda-d03f-480c-9cc2-a4de20abb878; socket option `HVSOCKET_CONNECTED_SUSPEND`. — [Make your own integration services](https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/user-guide/make-integration-service)
- Registration is needed when the host listens for guest connections; "This is not required if a guest listens for connections from the host"; "the connection itself can be run as a non-Administrator user". — [OCaml hvsock README](https://ocaml.org/p/hvsock/1.0.2/README.md.html)
- **Per-VM ACLs via HCS:** `HvSocketSystemConfig.DefaultBindSecurityDescriptor` ("SDDL string that HvSocket will check before allowing a host process to bind to an unlisted service for this specific container/VM (not wildcard binds)"), `DefaultConnectSecurityDescriptor`, `ServiceTable` of `HvSocketServiceConfig {BindSecurityDescriptor, ConnectSecurityDescriptor, AllowWildcardBinds}`; wildcard binds "are secured in the registry at SOFTWARE/Microsoft/Windows NT/CurrentVersion/Virtualization/HvSocket/WildcardDescriptors". — [HCS schema reference](https://learn.microsoft.com/en-us/virtualization/api/hcs/schemareference)
- **Go:** go-winio `HvsockAddr{VMID, ServiceID guid.GUID}`, `afHVSock = 34 // AF_HYPERV`, `ListenHvsock`, `HvsockGUIDWildcard()`, `HvsockGUIDChildren()`, `HvsockGUIDParent()`, `VsockServiceID(port)` (fills the facb template). — [go-winio hvsock.go (vendored mirror)](https://opensource.netapp.com/Cloud_Insights/2025-03-12_17:47:58/k8s-operators/github.com/Microsoft/go-winio/hvsock.go); also [linuxkit/virtsock hvsock](https://godocs.io/github.com/linuxkit/virtsock/pkg/hvsock)
- The WSL utility VM's ID (and other HCS VMs) can be found with `hcsdiag.exe list`. — [Ookii.VmSockets](https://feed.nuget.org/packages/Ookii.VmSockets/1.0.0-preview)
- WSL plugins communicate with Linux processes in the WSL VM "using a virtualized socket". — [WSL plugins](https://learn.microsoft.com/en-us/windows/wsl/wsl-plugins)
- **Filesystems:** WSLC: "Compared to plan9, virtiofs is about twice as fast"; Windows paths shared via virtiofs and bind-mounted. — [WSLC deep dive](https://devblogs.microsoft.com/commandline/?p=11811). Measured (nested lab): create 2,000 files virtiofs 21.7 s vs 9P 51.9 s; read 256 MB virtiofs 1.78 s vs 9P 15.1 s; VHD ext4 volume create 2,000 files 0.18 s (virtiofs ~120x slower than local ext4 for small files). — [ComputingForGeeks](https://computingforgeeks.com/?p=172378). Classic WSL `.wslconfig virtiofs` is experimental. — [WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config). HCS `Plan9` shares with `Port`, `AllowedFiles`; `VirtualSmb`. — [HCS schema reference](https://learn.microsoft.com/en-us/virtualization/api/hcs/schemareference). OpenVMM devices include virtio-fs and virtio-9p. — [OpenVMM guide](https://openvmm.dev/guide/user_guide/openvmm.html)
- WSLC Consommé networking runs in a user-mode Windows process; published ports bind to 127.0.0.1 by default (`-p 0.0.0.0:...` to expose). — [WSLC deep dive](https://devblogs.microsoft.com/commandline/?p=11811); [ComputingForGeeks](https://computingforgeeks.com/?p=172378)
- Windows Sandbox host<->guest: `wsb share` folder mapping; `wsb exec` without stdout. — [Windows Sandbox CLI](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-cli)

### Inferences
- Recommended no-listener pattern: **guest listens on AF_VSOCK, host connects** with AF_HYPERV (VMID of that VM + facb-template service GUID) — no HKLM registration, no TCP. For a QEMU/WHP VMM, the equivalent is a virtio-serial/vsock device backed by a Windows named pipe owned by the VMM process (QEMU chardev pipes; per-user DACL), which also avoids TCP. (QEMU named-pipe chardev support is prior knowledge, not verified this session.)
- For WSLC, use the SDK's process I/O handles instead of published ports; for classic WSL set `localhostForwarding=false` and avoid `0.0.0.0` binds.
- virtiofs/9P host shares are a large attack surface into the host filesystem; for agent VMs prefer per-agent VHD volumes and explicit copy-in/copy-out over the control channel.

### Gaps
- No primary source found for virtiofs host daemon availability on Windows for QEMU (virtiofsd is Linux-oriented); OpenVMM's Windows virtio-fs maturity unverified.
- Whether the WSL VM's HvSocket config lets the interactive user bind/connect arbitrary service GUIDs without registry entries was not confirmed.

## 9. Cross-option comparison (synthesis for the report writer)

### Takeaway
For "one small VM per agent with own FS, terminal and browser", the realistic Windows-native candidates in Oct 2026 are (1) **WSL containers (WSLC) sessions** (Microsoft-supported, per-user, GA, Linux, likely VM-per-session), (2) **a bundled VMM on WHP** (QEMU or OpenVMM; per-user process, Home-compatible, full control incl. snapshots), and (3) **direct HCS** (best primitives incl. clone-from-template, but needs Hyper-V Administrators or a SYSTEM broker). Windows Sandbox (single instance, Windows-only), Hyperlight (no OS) and Firecracker-in-WSL2 (unsupported nesting) do not meet the requirement.

### Cited Findings
- WSLC GA 29 Sep 2026, SDK 3.0.3 (13 Oct 2026), per-session VHD and observed per-session VM, cold start 34.1 s nested / 2.8-5.9 s warm, ~706 MB VM working set idle with nginx — [devblog](https://devblogs.microsoft.com/commandline/?p=11811); [NuGet](https://www.nuget.org/packages/Microsoft.WSL.Containers); [ComputingForGeeks](https://computingforgeeks.com/?p=172378)
- WHP user-mode VMM model (memory via VirtualAlloc in the VMM process, vCPU threads) — [WHP API](https://learn.microsoft.com/en-us/virtualization/api/hypervisor-platform/hypervisor-platform); QEMU WHPX status — [QEMU docs](https://www.qemu.org/docs/master/system/whpx.html)
- HCS privilege rule and save/clone primitives — [HCS error codes](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hcshresult); [HCS schema](https://learn.microsoft.com/en-us/virtualization/api/hcs/schemareference)
- Windows Sandbox single instance, Pro+ only, CLI 24H2+, ~500 MB base image — [overview](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/); [architecture](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-architecture)
- Hyperlight no OS/no network/no FS, pre-1.0; Nanvix double-digit-ms cold start — [Hyperlight](https://github.com/hyperlight-dev/hyperlight); [Nanvix blog](https://opensource.microsoft.com/blog/2026/1/28/github.com/hyperlight-dev/hyperlight-nanvix)
- Microsoft: non-Microsoft virtualization nested on Hyper-V unsupported — [nested virtualization](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/nested-virtualization)
- MXC bundles several of these as backends (`processcontainer`, `windows_sandbox`, `wslc`, `microvm`, `hyperlight`, `isolation_session`) — [microsoft/mxc](https://github.com/microsoft/mxc)
