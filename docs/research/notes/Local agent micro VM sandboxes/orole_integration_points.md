# Orole OS integration points for a per-agent sandbox VM (own filesystem, terminal, browser)

All sources are files in the repository at `C:/code/projects/orole-os` (branch `jarvis-mode`, read on 2026-10-15). Links are relative to this notes file (`../../` = repo root). Line numbers refer to the working tree at the time of reading, which has uncommitted changes. Nothing was run; this is a read-only code and docs survey.

## 1. Architecture rules and hard constraints a sandbox must respect

### Takeaway
Orole has three layers: React UI, a stateless MyGo desktop bridge, and a per-user headless daemon that owns all state, processes and permission decisions. The daemon talks only over an authenticated named pipe; it never listens on a network interface. Secrets go only to Windows Credential Manager, and external content is always data. A sandbox VM therefore has to be a daemon-owned resource, managed and policy-checked in Go, reached over a non-network or client-only transport, with platform code kept in `_windows.go` files or `internal/platform`. The repo states outright that no OS, container or VM isolation exists today.

### Cited Findings
- Binding rules: React is UI only and not a security boundary; `internal/app` is stateless; durable state, agents, terminals, automations and MCP connections live in the daemon, "never in the GUI process" — [AGENTS.md:6-9](../../AGENTS.md)
- "Permissions are decided by the Go side. Never add a frontend-only check for a sensitive action." — [AGENTS.md:10](../../AGENTS.md)
- Secrets go only to Windows Credential Manager via `internal/credentials`: "Never SQLite, logs, env dumps, or the frontend." — [AGENTS.md:11](../../AGENTS.md); [docs/architecture/credentials.md:3,30-31](../../docs/architecture/credentials.md)
- "No listener on a network interface. IPC is a per-user pipe (DACL = current user SID) + token." — [AGENTS.md:12](../../AGENTS.md). Pipe name `\\.\pipe\orole-daemon-<SID>-<hash>`, DACL with a single ACE; "There is no TCP/HTTP listener." — [docs/architecture/ipc-protocol.md:8-14](../../docs/architecture/ipc-protocol.md)
- Allowed exceptions: OAuth callbacks and explicitly enabled signed webhooks bind to loopback only, and WebView2 CDP is opt-in loopback for acceptance testing only — [docs/architecture/security-permissions.md:11](../../docs/architecture/security-permissions.md)
- External content (mail, issues, Drive, MCP results, repo instructions) is untrusted data — [AGENTS.md:13](../../AGENTS.md). `internal/untrusted` strips control and bidi characters; `internal/policy` is the central gate — [docs/architecture/overview.md:54-56](../../docs/architecture/overview.md). Prompt-injection rules: wrap external text as fenced data, never let it choose tools, targets or approvals; repo instruction files cannot widen permissions — [docs/security/threat-model.md:69-80](../../docs/security/threat-model.md)
- No mock data. An unconfigured integration shows a setup screen and an unbuilt module returns `NotImplemented` — [AGENTS.md:14](../../AGENTS.md)
- "Platform code only under `internal/platform/*` or `_windows.go`/`_unix.go` files behind interfaces." — [AGENTS.md:15](../../AGENTS.md)
- Honest persistence: terminal sessions survive GUI restarts but not daemon exit or reboot, and the UI and docs must say so — [AGENTS.md:16](../../AGENTS.md); [docs/decisions/0006-conpty-and-honest-persistence.md:10-17](../../docs/decisions/0006-conpty-and-honest-persistence.md)
- Layer table: the daemon owns "SQLite, terminals, integrations, permission decisions, audit log" and must not "listen on a network interface". The desktop process owns the window and desktop-side OS integration (autostart, diagnostics) — [docs/architecture/overview.md:22-27](../../docs/architecture/overview.md)
- The daemon runs as a normal per-user process in the interactive session, never elevated and never a Session 0 service. It starts via a per-user Task Scheduler task with `RunLevel=LeastPrivilege` because shells, git and agents must see the user's profile, HKCU and Credential Manager — [docs/architecture/windows-runtime.md:3-4,19-24,37-51](../../docs/architecture/windows-runtime.md)
- Service pattern: each module is `internal/daemon/svc_<name>.go` with `register<Name>()`, called from `registerServices()`. Methods use `handle[P,R](d, "name", ...)`, and sensitive actions call `d.audit(...)` — [docs/architecture/daemon.md:22-26](../../docs/architecture/daemon.md); registration order in [internal/daemon/services.go:20-44](../../internal/daemon/services.go)
- `orole-cli` is a thin IPC client and must not link the daemon, sqlite, sftp/ssh or the MCP SDK (enforced by `scripts/check-cli-linkage.sh`) — [docs/architecture/daemon.md:117-118](../../docs/architecture/daemon.md)
- IPC: newline-delimited JSON with a 4 MiB frame cap; `hello` with a 32-byte token comes first; each call has a 30 s default deadline; each subscriber has a bounded 256-frame queue; additive changes keep protocol version 1 — [docs/architecture/ipc-protocol.md:18-19,32-36,49-50,59-62,86-87](../../docs/architecture/ipc-protocol.md)
- Changing a bound service means running `go tool mygo generate` and committing `frontend/src/mygo.ts`. New widgets register in `components/widgets/registry.tsx` and commands in `lib/commands.ts`. No native `title` attributes; use the Tooltip component instead. Copied upstream code is recorded in `docs/research/upstream-attribution.md` — [AGENTS.md:37-48](../../AGENTS.md)
- Migrations are embedded, forward-only and numbered, each applied in its own transaction, with no down migrations — [docs/architecture/database-schema.md:8-15](../../docs/architecture/database-schema.md). The latest file is `0111_jarvis_bot_reported.sql` — [migrations/](../../migrations/)
- No isolation exists today. The agent manager's authorizer "does not sandbox an agent's process: worktree separation is not OS isolation" — [docs/architecture/security-permissions.md:65-69](../../docs/architecture/security-permissions.md). The threat model says: "Agent worktrees separate changes; they do not isolate credentials, the host filesystem or the network from an approved process. Untrusted local agents require a separately reviewed OS/container/VM boundary; no Windows Sandbox backend is claimed here." — [docs/security/threat-model.md:86-88](../../docs/security/threat-model.md). Approving a local CLI "does not sandbox its process" — [docs/security/threat-model.md:40](../../docs/security/threat-model.md)
- The same disclaimer appears for the other execution surfaces. Machine commands: "file roots are not an execution sandbox" — [docs/architecture/machines.md:29](../../docs/architecture/machines.md). The application launcher "is not a sandbox" — [docs/architecture/desktop-integration.md:17](../../docs/architecture/desktop-integration.md). Remote agent processes: "Full remote account permissions; approved roots select cwd, not a sandbox." — [internal/machines/agent_process.go:371](../../internal/machines/agent_process.go)

### Inferences
- A sandbox manager must be a daemon module (`svc_sandbox.go` + `registerSandbox()` + an `internal/sandbox` package). The GUI only binds an `app.Sandboxes{L: link}` bridge, following the `app.Machines` pattern ([internal/app/machines.go:9-67](../../internal/app/machines.go)).
- VM lifecycle (create, start, stop, destroy, snapshot) changes the machine and should go through `policy.Check` as `write` or `destructive` effects with audit entries. Destroying a VM, discarding its disk, or giving it network access or host-folder mounts look like `destructive` or trust-changing approvals, like machine pairing and access grants ([docs/architecture/machines.md:16-17,25](../../docs/architecture/machines.md)).
- The guest's control channel must not be a host listener on a network interface. Plausible fits are the daemon acting as a client (for example SSH into the guest, or Hyper-V sockets / AF_VSOCK, where the daemon dials the guest), or a named pipe with a user-only DACL. Any host-side TCP port forward for a guest browser or dev server would conflict with AGENTS.md:12 unless it is loopback-only and justified like the OAuth and webhook exceptions.
- Hypervisor-specific code (HCS, Hyper-V, WSL) must sit behind an interface in `_windows.go` files or `internal/platform`. Non-Windows builds need a stub that returns an explicit "unsupported" error, in the style of `credentials/store_other.go` ([docs/architecture/credentials.md:17-18](../../docs/architecture/credentials.md)).
- Honest persistence applies. The UI and docs must state exactly what survives a GUI restart, a daemon restart and a reboot: a VM can outlive the daemon, unlike job-object processes.

### Gaps
- No ADR or spec exists for sandboxing. `docs/decisions/` stops at 0007 and `docs/superpowers/specs` holds only the Jarvis spec, so nobody has decided whether a hypervisor-managed VM counts as an allowed "platform" dependency or needs admin rights. The daemon is designed never to need elevation ([docs/architecture/windows-runtime.md:46-47](../../docs/architecture/windows-runtime.md)), and enabling Hyper-V or WSL features normally does. That tension is unresolved in the repo.

## 2. The two kinds of agents: chat bots versus code tasks (where they run and how they get tools)

### Takeaway
Chat bots are LLM tool loops that run inside the daemon. They have no shell or file access; their tools are Go `chat.Tool` implementations such as web fetch, research, MCP proxies, skills, memory and code tasks. Code tasks run CLI harnesses (Claude Code, Codex, Oh My Pi, OpenCode, Gemini, custom) as child processes of the daemon on the host, inside a Windows job object, with the daemon's environment and full user permissions. Structured local sessions get Orole's MCP gateway and skills index. Remote (SSH) sessions get neither. A bot reaches a shell only by starting a code task.

### Inferences
- A sandbox is most naturally a third execution location for code tasks, next to `local` and SSH `remote`. Every `localMachine(...)` branch in `internal/agents/manager.go` (Start, launch, restart, diff/review, attachments, worktrees) is a decision point that would need a sandbox case. A `Location`/`Runner` abstraction would be cleaner than adding a third boolean branch at each site.
- Code tasks are the only agents that need a VM filesystem and terminal. For bots, a sandbox would most plausibly appear as (a) the place their code tasks run, and (b) new `chat.Tool`s such as a "sandbox browser" or "sandbox shell" registered in `registerChatTools`, policy-checked with actor `bot:<id>`.
- Gateway, skills and Claude hooks all assume the harness can reach the daemon's named pipe. Inside a VM a harness cannot. Options:
  - Run `orole-daemon mcp-gateway` on the host per session and bridge its stdio into the guest over the guest control channel. The harness config inside the guest would point at a small stdio relay.
  - Implement a second `gateway.Backend` that tunnels `gateway.*` calls over the sandbox channel.

  Either way the actor stays `agent:<sessionID>` and policy is unchanged. This matters: without it, sandboxed sessions lose skills and MCP tools, which is the current state for remote sessions.
- Claude subscription credentials live in the CLI's own config on the host ("Orole never reads, stores or logs them" — [docs/architecture/cli-runtimes.md:3-5](../../docs/architecture/cli-runtimes.md)). A guest harness needs its own sign-in or an explicit, approved credential hand-off. Copying host CLI tokens into a guest would conflict with the credentials rules.

### Gaps
- No code or doc defines how a harness inside an isolated environment would authenticate to its vendor, or how the gateway would be reached from a non-pipe environment. This is new design work.

## 3. `internal/machines` (SSH machines): what exists, remote code tasks, keys, files and terminals, and VM-as-machine

### Takeaway
`internal/machines` is a daemon-owned registry of execution "boxes". `local` is native; paired remote hosts use pinned-host-key SSH and SFTP with keys in Credential Manager. It supports policy-gated commands, SFTP file access under approved roots, and one-shot remote Claude/Codex runs in `process` mode. It has no terminals, no worktrees, no gateway, no structured approvals and no resume. A local VM running sshd could technically be paired as a remote machine today and would inherit all of those limits. The `Machine` schema (`kind`, `transport`, `backend`) and the `files.Provider`/`remote` provider are the obvious reuse points for a richer sandbox-as-machine.

### Cited Findings
- Ownership: the daemon owns `machines.Manager`, metadata, SSH credentials and command cancellation; `internal/app.Machines` is a stateless bridge. `machines.NewProvider` registers the Files `remote` provider — [docs/architecture/machines.md:5](../../docs/architecture/machines.md)
- Local identity is `local`, initialized from the real hostname and OS. Remote uses `x/crypto/ssh` + `pkg/sftp`; "no Tailscale, network listener, or remote Orole daemon is required." — [docs/architecture/machines.md:7](../../docs/architecture/machines.md); [internal/machines/machines.go:103-111](../../internal/machines/machines.go)
- Transport and execution are separate fields: native/native; SSH/POSIX for Linux; SSH/PowerShell for Windows — [docs/architecture/machines.md:9](../../docs/architecture/machines.md)
- `Machine{ID, Name, Kind, OS, Transport, Backend, Address, Username, Fingerprint, Roots, AllowCommands, AllowWrite, CreatedAt, hostKey, accessRevision}` — [internal/machines/machines.go:31-47](../../internal/machines/machines.go). Table: `machines(id, name, kind -- local|remote, os, transport, address, fingerprint, created_at)` — [migrations/0001_init.sql:16-25](../../migrations/0001_init.sql). Later added `backend`, `username`, `host_key`, `roots`, `allow_commands` and `allow_write` — [migrations/0070_machines.sql:1-6](../../migrations/0070_machines.sql); `access_revision` — [migrations/0092_machine_access_revision.sql:1](../../migrations/0092_machine_access_revision.sql)
- Pairing: the user enters host, port, account, OS and an unencrypted OpenSSH private key path. `Probe` reads the host key as untrusted discovery; the user pastes an independently verified SHA256 fingerprint; pairing is a destructive policy approval. The private key goes into the credential store under `machines/<id>/key` and is never returned through IPC or stored in SQLite. Pairing grants no roots, writes or commands — [docs/architecture/machines.md:11-17](../../docs/architecture/machines.md)
- Every dial loads the key just-in-time from the credential store, pins both fingerprint and exact host-key bytes, and requires `Kind=="remote" && Transport=="ssh"` — [internal/machines/ssh.go:171-193](../../internal/machines/ssh.go). A changed key fails closed — [docs/architecture/machines.md:19](../../docs/architecture/machines.md)
- Authorization: resource `machine/<id>`, action `machines.<op>` — [internal/machines/machines.go:90-102](../../internal/machines/machines.go)
  - Reads use `machines.files.read`.
  - Writes need the per-machine write grant plus `machines.files.write`.
  - Commands need the command grant plus `machines.execute`, classified destructive.

  Local Files roots and machine roots never authorize each other — [docs/architecture/machines.md:25](../../docs/architecture/machines.md)
- Commands are argv only: native `exec.CommandContext`, POSIX single-quoting on Linux, and an encoded PowerShell .NET-Process bootstrap on Windows. Timeout defaults to 30 s with a 300 s cap; stdout and stderr are each capped at 512 KiB; operations are cancelable by UUID — [docs/architecture/machines.md:29-31](../../docs/architecture/machines.md); [internal/machines/execute.go:25-110,186](../../internal/machines/execute.go)
- Files: `machines.NewProvider` implements `files.Provider` as `remote` with namespace `/<machine-uuid>/<path>`. It supports list, stat, bounded read, optimistic atomic write and search. Mkdir, rename and delete return `ErrUnsupportedOp`. Calls share one pooled SSH+SFTP connection per machine, and authorization is never cached — [docs/architecture/machines.md:35-41](../../docs/architecture/machines.md); [internal/machines/provider.go:15-164](../../internal/machines/provider.go); [internal/machines/pool.go:18-115](../../internal/machines/pool.go)
- Remote code tasks: only `claude` and `codex`, only `ModeProcess`, no `NewWorktree`, and a prompt is required — [internal/agents/manager.go:621-633](../../internal/agents/manager.go). `startRemote` rejects resume and any non-process mode. Its system note reads: "No local terminal, structured approvals, or worktree review is available. Disconnecting cannot guarantee that remote descendants stop." Output is capped at 512 KiB with a 16 KiB tail — [internal/agents/remote.go:12-87](../../internal/agents/remote.go)
- Remote launch: probes the CLI with `--version`/`--help` over SSH and requires `AllowCommands` — [internal/machines/agent_process.go:47-118](../../internal/machines/agent_process.go). Builds `claude --print --output-format text --permission-mode default|auto|plan` or `codex exec --sandbox workspace-write ... -` — [internal/machines/agent_process.go:214-262](../../internal/machines/agent_process.go). Runs `cd <dir> && <cmd>` (POSIX) or an encoded PowerShell process with the prompt on stdin — [internal/machines/agent_process.go:264-284](../../internal/machines/agent_process.go). The process lives under a 24 h lifetime and an access snapshot — [internal/machines/agent_process.go:290-300](../../internal/machines/agent_process.go)
- Remote permission modes: Manual only for Codex; Manual and Auto for Claude when advertised; never YOLO — [internal/agents/permission_modes.go:87-99](../../internal/agents/permission_modes.go)

### Inferences
- **VM as a "machine" today:** a guest with sshd reachable from the host (for example on a Hyper-V internal switch or WSL2 NAT) could be paired with the existing flow. It would get only process-mode Claude/Codex, SFTP files under approved roots, and one-shot commands. Manual fingerprint verification makes sense for foreign hosts but is redundant for a VM the daemon itself provisioned.
- **Better fit:** a new machine `kind` (for example `sandbox`) and `transport` (for example `hvsock`/`vsock`/`ssh-internal`) whose identity, host key and client key the daemon generates when it builds the VM. The key still goes in Credential Manager under `machines/<id>/key` or `sandbox/<id>/key`. Such a machine reuses `Machine` rows, `files.Provider` ("remote"-style namespace or a new `sandbox` provider ID), `Execute`, policy resource `machine/<id>`, and the footer, picker and environment UI. This needs a migration (for example `0112_sandboxes.sql`) adding VM-specific columns or a separate `sandboxes` table keyed to `machines.id`.
- The binary `localMachine()` split in agents would need a third path so sandboxed sessions can be structured, with approvals and the gateway, rather than one-shot `process` runs. Running structured protocols such as `claude -p --output-format stream-json` or `codex app-server` over an SSH session's stdin and stdout looks feasible, because `pipeProc` only needs an `io.Reader`/`io.Writer` pair ([internal/agents/adapter.go:296-348](../../internal/agents/adapter.go)). Today it is built on `exec.Cmd`.
- Worktree review (`Diff` and `Review`) refuses non-local sessions (`errRemoteOperation`, [internal/agents/manager.go:1776-1777](../../internal/agents/manager.go)). A sandbox design that keeps the git worktree on the host and shares it read-write into the guest keeps review working. A design that copies the repo into the guest needs a diff export step.

### Gaps
- It is unclear whether the removed MachinesView will return. With no pairing UI, there is no user-facing path to add any non-local box today, sandbox or otherwise.

## 4. `internal/terminals`: daemon-owned terminals on Windows (ConPTY) and Linux (PTY/tmux), and surfacing a VM terminal

### Takeaway
`terminals.Manager` is backend-agnostic. It owns sessions, the 1 MiB scrollback ring, output pacing, sequence-numbered reattach and owner tagging. It drives one `Backend{Start, Shells}` returning `Process{Read, Write, Resize, Wait, Pid, Close}`, with optional capability interfaces such as tmux persistence. A VM terminal fits naturally as a `Process` implementation backed by a guest PTY over the sandbox channel (SSH `RequestPty` or a vsock agent). The manager currently holds a single backend per daemon, so per-session backend selection would have to be added.

### Cited Findings
- `Backend{Start(StartSpec) (Process, error); Shells() []Shell}`. `Process{Read; Write; Resize(cols, rows); Wait(ctx) (exitCode, error); Pid(); Close()}`. `StartSpec{Command, Cwd, Env, Cols, Rows}` — [internal/terminals/terminals.go:18-42](../../internal/terminals/terminals.go)
- `Info` carries `Owner` (for example `agent:<id>`) and `PersistentID` — [internal/terminals/terminals.go:60-74](../../internal/terminals/terminals.go)
- Limits: `ScrollbackBytes = 1 MiB`, 64 running sessions, 16 exited sessions kept for 30 min, about 2 MiB/s per-session event pacing — [internal/terminals/terminals.go:96-110](../../internal/terminals/terminals.go)
- `Manager{be Backend, sink Sink, ...}` and `NewManager(be, sink)` hold one backend per manager — [internal/terminals/terminals.go:117-133](../../internal/terminals/terminals.go). The daemon builds exactly one with `terminals.NewManager(terminals.NewBackend(), termSink{d})` — [internal/daemon/daemon.go:105](../../internal/daemon/daemon.go)
- `CreateOptions{Shell, Cwd, Cols, Rows, Title, Owner, Command, Persistence}`. `Persistence` is `""` (daemon lifetime) or `"tmux"`, chosen through an optional `persistentBackend` interface — [internal/terminals/terminals.go:168-248](../../internal/terminals/terminals.go); [internal/terminals/persistence.go:12-27](../../internal/terminals/persistence.go)
- Windows backend: `conpty.Start(command, dims, workdir, env)`. `winProc.Close` kills the root and closes the pseudoconsole exactly once, because a double close corrupts the heap — [internal/terminals/backend_windows.go:17-57](../../internal/terminals/backend_windows.go)
- Shells detected: powershell, pwsh, cmd, git-bash. Exited sessions stay attachable. `terminals.attach` returns scrollback plus `seq`, so reattach is lossless — [docs/architecture/windows-terminals.md:8-37](../../docs/architecture/windows-terminals.md)
- Linux backend: `creack/pty`, `/bin/sh -c` command lines, `TERM=xterm-256color` — [docs/architecture/linux-terminals.md:3-25](../../docs/architecture/linux-terminals.md)
- Opt-in tmux persistence survives daemon exit but not reboot. It uses a per-home isolated socket and `/dev/null` config, and it is "isolation of application instances, not a security boundary" — [docs/architecture/linux-terminals.md:27-46,50-60,80-90](../../docs/architecture/linux-terminals.md)
- The Linux terminal package was accepted on Ubuntu WSL with Go 1.27.1 — [docs/architecture/linux-terminals.md:121-124](../../docs/architecture/linux-terminals.md)
- UI-created terminals have `Owner` and `Command` stripped, and only daemon code may set them; `terminal.create` is audited — [internal/daemon/services.go:120-129](../../internal/daemon/services.go); [docs/architecture/security-permissions.md:13](../../docs/architecture/security-permissions.md)
- Agent terminal-mode sessions use owner `agent:<session-id>` and are "inspectable in the session's Terminal tab" — [docs/architecture/windows-terminals.md:131-136](../../docs/architecture/windows-terminals.md)
- Frontend state: `features/terminals/TerminalPane.tsx` (xterm.js attach/write/resize via `Terminals.*`) still exists but nothing imports it. `TerminalsView.tsx` was deleted in `f869ebe` — [frontend/src/features/terminals/TerminalPane.tsx:36-110](../../frontend/src/features/terminals/TerminalPane.tsx). xterm 6 is a dependency — [frontend/package.json:43-47](../../frontend/package.json)
- Shipyard reference: its session host is tmux on Linux boxes. The Orole replacement direction is "Own session manager in orole-daemon: ConPTY child + in-memory ring buffer ... reattach = daemon-held PTY" — [docs/research/shipyard-analysis.md:381-383](../../docs/research/shipyard-analysis.md)

### Inferences
- A guest terminal is a `terminals.Process` whose reads and writes go to a PTY inside the VM, for example an `ssh.Session` with `RequestPty` plus `WindowChange` for `Resize`, or a small guest agent over vsock. `Pid()` would be the guest PID or 0, and `Close()` would kill the guest process group.
- Two wiring options:
  - Let `CreateOptions` carry a target (for example `Sandbox string`) and have the manager route to a per-target backend, in the same style as the optional `persistentBackend` interface.
  - Register a `Backend` per sandbox inside a composite backend.

  Either way the existing event, scrollback, owner (`agent:<id>` / `sandbox:<id>`), `terminal.output` protocol and xterm UI work unchanged.
- Persistence semantics change. A tmux server inside the VM survives a daemon restart while the VM keeps running, like the Linux tmux option. The VM also outlives host-job semantics: it is not in the agent's job object, so "processes die with the daemon" no longer holds automatically. UI and docs must state the real lifetime.
- There is currently no reachable frontend place to view a standalone terminal. The task view (`features/tasks`) or the session rail would have to host a guest terminal tab.

### Gaps
- `Terminal tab` for agent sessions is described in the docs, but no current importer of `TerminalPane` was found, so how terminal-mode agent sessions are shown in today's UI could not be confirmed from code.

## 5. Policy, bot tool access, approvals, files, the automation command runner, platform and cliruntime

### Takeaway
`internal/policy.Engine` is the single gate. It takes an actor, action, resource and effect (read/write/destructive), applies stored rules and per-tool MCP permissions, and falls back to defaults: read allows, write and destructive ask, unclassified denies. `ask` parks the request for UI approval, and every decision is audited. Bot tool access (ask/read/write/all) is an auto-approve hook that lifts only default asks for `bot:<id>`. Files are guarded by canonicalized approved roots behind a `files.Provider` registry. Automation commands are argv-only with an executable allowlist and policy approval. `internal/platform` currently holds only autostart and WebView2 detection. `internal/cliruntime` installs vendor CLIs per OS/arch under `<data>/cli/<id>/<version>/`. All of these are reusable for a sandbox; the sandbox mostly adds new actions and resources to policy, a new files provider, and a guest-target CLI install.

### Cited Findings

### Inferences
- Sandbox lifecycle should use new policy actions such as `sandbox.create`, `sandbox.start`, `sandbox.destroy`, `sandbox.network`, `sandbox.mount` and `sandbox.exec`, on resources `sandbox/<id>` (or the existing `machine/<id>`). Destroy, network-enable and host-mount should be destructive. Bot-originated requests then flow through the same auto-approve hook and inline approval cards.
- A per-sandbox `files.Provider` (ID `sandbox`, namespace `/<sandbox-id>/<path>`) registered through `reg.Register(...)` would expose the guest filesystem in the Files UI with no UI framework changes.
- `automations.CommandRunner` is an interface. A sandbox-backed runner (or a `sandbox` field in `command.run` steps) would let automations run test commands inside a VM. This fits the existing destructive classification and allowlist.
- `cliruntime.New(Config{GOOS: "linux", GOARCH: <guest arch>, StoreDir: <data>/sandbox/cli})` could fetch hash-verified Linux harness binaries for injection into a guest image. However, `Install` verifies by executing the binary on the host, which fails for a Linux binary on a Windows host. A guest-side version check, or a skip-execution mode, would be needed.
- New hypervisor glue (HCS or `wsl.exe` invocation, Hyper-V socket dialing) belongs in `internal/platform` (for example `vm.go` with an interface, plus `vm_windows.go` and a `vm_other.go` stub) or in `internal/sandbox/*_windows.go`. Either satisfies AGENTS.md:15.

### Gaps
- No existing code sets resource limits (CPU, memory, disk, network) on agent processes. Job objects are used only for kill-on-close ([internal/agents/job_windows.go:30-35](../../internal/agents/job_windows.go)), so there is no precedent for quotas.

### Inferences
- **Package placement:**
  - `internal/sandbox` (types `Sandbox`, `Image`, `Spec{CPU, MemoryMB, DiskGB, Network, Mounts}`, `Manager`, a `Hypervisor` interface) with `hypervisor_windows.go` (HCS, Hyper-V or WSL2) and `hypervisor_other.go` (an explicit "unsupported" error).
  - `internal/daemon/svc_sandbox.go` for IPC `sandbox.*` and events `sandbox.changed`.
  - A migration `0112_sandboxes.sql`.
  - `internal/app/sandboxes.go`, then `go tool mygo generate`.
- **Agent integration:** a `StartSpec.Sandbox` field (or `Machine: "sandbox:<id>"`) plus a `Location` interface in agents with `Start(ctx, Host, LaunchSpec) (Process, error)`, `Gateway()`, `Files()` and `Terminals()` implementations for local, ssh and sandbox. The local path stays the default. This avoids scattering `localMachine` checks further.
- **Per-agent VM semantics:** one VM per task session (or per worktree, as Shipyard does per worktree) with the session's worktree shared in. The VM ID is recorded on `agents.Session` (a new column), and the VM is destroyed or kept per user setting when the task is removed. This matches the existing `WorktreeOwned` cleanup semantics ([internal/agents/types.go:85-86](../../internal/agents/types.go)).
- **UI surfaces:**
  - A "Run in sandbox" option in the Home "Run on" picker and the New task view.
  - A Sandbox block in the session rail Environment section (VM state, resources, network, terminal and browser tabs).
  - A sandbox default in Settings › Task permissions (for example "Run Yolo tasks only in a sandbox"; a bot-specific default under "Bot code tasks").
  - A guest Files root.
  - Footer status entries.
  - A new Settings or System page for images, disk use and cleanup, since the old Machines page is gone.

  Unbuilt parts should return `NotImplemented` or a setup screen per AGENTS.md:14.

### Gaps
- No product decision exists on whether sandbox VMs are per task, per bot or per project. No requirement exists for guest OS (Linux vs Windows) or for how worktree changes return to the host. These choices drive whether review and diff keep working unchanged.
