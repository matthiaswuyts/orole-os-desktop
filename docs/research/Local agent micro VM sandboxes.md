# Give every Orole agent its own computer

Orole should not chase Firecracker on Windows. The best design is a two-tier, daemon-owned sandbox service. **Tier 1** is host process containment for every code task. It ships first and runs on the developer's build 22000 today. **Tier 2** is a per-agent Linux micro VM with its own disk, PTY and headful Chromium. Run it as a plain per-user VMM process on the **Windows Hypervisor Platform (WHP)**, starting with bundled QEMU, and reach it only over a named pipe or virtual serial channel, with no virtual NIC. Firecracker is Linux/KVM-only. On Windows it runs only nested inside WSL2, which Microsoft and the Firecracker maintainers both call unsupported. Hyper-V's Host Compute Service has the best primitives, but it needs Hyper-V Administrators membership or a SYSTEM broker. Windows Sandbox runs one instance at a time. Microsoft's new MXC/PSEC containment and its WSL containers are the forward path, but they are not available, or not documented, for build 22000. The market has converged on one pattern, and Orole's architecture already has most of the seams to host it: hardware VM per agent, in-guest control daemon, host-side allowlisting proxy, and credentials injected outside the guest. The plan below adds a fourth execution location (`sandbox`) beside `local` and SSH, and plugs it into the existing `agents`, `terminals`, `files`, `policy`, `gateway` and `chat.Tool` interfaces. The developer machine is the biggest practical obstacle. Windows 11 21H2 went out of servicing on 2023-10-10 and lacks several features. It can build and test Tier 1 and the QEMU/WHP backend, but nothing newer.

## Orole has zero isolation today, and its rules dictate the shape of the fix

The repo is explicit that no boundary exists. The agent authorizer "does not sandbox an agent's process: worktree separation is not OS isolation" ([security-permissions.md](../docs/architecture/security-permissions.md)). The threat model says untrusted local agents "require a separately reviewed OS/container/VM boundary; no Windows Sandbox backend is claimed here" ([threat-model.md](../docs/security/threat-model.md)). Code tasks run Claude Code, Codex, Oh My Pi, OpenCode and Gemini on the host as daemon children. They inherit the daemon's whole environment, sit in a Windows job object used only for kill-on-close, and have full user rights ([adapter.go](../internal/agents/adapter.go); [job_windows.go](../internal/agents/job_windows.go)). The only confinement in use is whatever each harness brings, such as Codex's own `workspace-write` mode ([codex_appserver.go](../internal/agents/codex_appserver.go)). Chat bots are different. They are LLM tool loops inside the daemon with no shell or file access, and they reach a shell only by starting a code task ([chat.md](../docs/architecture/chat.md)). So "every agent gets a computer" means two things. Code tasks need a contained place to run. Bots need new sandboxed tools (shell, browser) that they currently lack.

Orole's architecture rules narrow the options before any technology is compared. A sandbox must be a **daemon-owned resource** whose lifecycle is decided by `policy.Check` in Go and audited. Its platform code must sit in `_windows.go` files or `internal/platform`. Secrets must stay in Credential Manager. Above all, there must be **no listener on a network interface**, because IPC is a per-user pipe with a user-SID DACL ([AGENTS.md](../AGENTS.md); [ipc-protocol.md](../docs/architecture/ipc-protocol.md)). The daemon also runs unelevated, as a per-user Task Scheduler task with `RunLevel=LeastPrivilege` ([windows-runtime.md](../docs/architecture/windows-runtime.md)). Any design that needs admin rights at runtime, or a TCP port for guest control, browser debugging or live view, starts at a disadvantage. That alone rules out several popular patterns: noVNC over `ws://`, the xterm.js attach addon, WebRTC streamers such as neko, and CDP on `--remote-debugging-port`. Each needs an IP listener the UI can reach.

## Firecracker needs a Linux host, so on Windows it means unsupported nesting

Firecracker is still the reference microVM. It reaches guest `/sbin/init` in **125 ms or less** with **5 MiB or less** of VMM overhead ([SPECIFICATION.md](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md)), and snapshot/restore went GA in v1.13 ([CHANGELOG](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)). But it requires read/write `/dev/kvm` and has no Windows or WHP backend. Its maintainers place nested virtualization "outside Firecracker's scope" ([firecracker#1721](https://github.com/firecracker-microvm/firecracker/issues/1721)). On Windows 11, WSL2 does expose nested KVM by default. The 6.18 WSL kernel ships the KVM modules, and Windows 11 satisfies the AMD nesting floor, so build 22000 qualifies on both Intel and AMD ([boxofcables, Jun 2026](https://www.boxofcables.dev/build-a-custom-wsl-2-kernel-in-2026/); [Microsoft nested virtualization](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/enable-nested-virtualization)). Microsoft is equally blunt from its side: "Non-Microsoft virtualization on Hyper-V virtualization isn't supported" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/nested-virtualization)). The research found **no 2025–2026 production user or benchmark** of Firecracker or Cloud Hypervisor inside WSL2.

The operational fit is worse than the support story. Every nested microVM would live inside the **single WSL utility VM**. That VM has one memory cap (50% of host RAM by default), a 60-second `vmIdleTimeout`, and a `wsl --shutdown` that kills everything ([WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)). Agent lifetime would then depend on WSL's lifecycle rather than the daemon's. Mirrored networking needs 22H2+, so on 22000 the result is double NAT. Docker reached the same conclusion for its own product: it wrote a custom VMM for Docker Sandboxes because Firecracker targets only Linux deployments ([Cloud Native Now](https://cloudnativenow.com/contributed-content/the-questions-every-team-asks-about-docker-sandboxes/); [Docker blog](https://www.docker.com/blog/why-microvms-the-architecture-behind-docker-sandboxes/)). The same objection applies to Cloud Hypervisor and Kata. Their MSHV support means a Linux root partition on the Microsoft Hypervisor, not a Windows 10/11 host ([CH mshv.md](https://git.phyllo.me/External/cloud-hypervisor/src/tag/v42.0/docs/mshv.md)). gVisor's `systrap` platform is the one Linux sandbox that runs in WSL2 without nested KVM ([gVisor platforms](https://gvisor.dev/docs/architecture_guide/platforms)). It still inherits the shared-VM lifecycle, so it is at most a fallback. Firecracker's design lessons still apply locally even though Orole should not use the binary: read-only base image plus per-instance overlay ([E2B](https://www.e2b.dev/blog/scaling-firecracker-using-overlayfs-to-save-disk-space)), and the clone-uniqueness rules for snapshots ([snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)).

## WHP is the only VM path that is per-user, Home-compatible and testable on build 22000

The Windows-native options differ mainly in who must be privileged. The table below summarises the research. "One-time admin" means a DISM feature enable plus reboot, which every option needs.

| Option | Guest | VM per agent | Admin at runtime | Works on 22000 | Snapshot / clone | Fit for Orole |
|---|---|---|---|---|---|---|
| QEMU / OpenVMM on WHP | Any Linux + Chromium | Yes | No | Yes (QEMU x86 tested from Win10 2004) | QEMU qcow2/savevm | **Best now**: per-user process, daemon-owned, Home-compatible |
| WSL containers (WSLC) SDK | Linux containers in a session VM | Observed, not Microsoft-stated | No (per-user `wslcsession.exe`) | Undocumented | VHD copy / image commit only | **Strong second**: supported and GA, but unverified on 21H2 |
| Direct HCS (hcsshim) | Linux or Windows utility VM | Yes | Hyper-V Administrators or SYSTEM broker | Yes (API since 1809) | Yes: save-to-file, clone-from-template | Best primitives, worst privilege story |
| Classic WSL2 distro per agent | Linux | No (shared VM and kernel) | No | Yes | `--export`/`--import` | Container-grade only |
| Windows Sandbox | Windows only | No (one instance) | No | `.wsb` only; CLI needs 24H2 | Disposable | One shared desktop at most |
| Hyperlight / Nanvix | No OS / POSIX microkernel | Per function | No | Unknown | Yes | Cannot run a shell or browser |
| Firecracker / CH in WSL2 | Linux | Nested | No | Yes on Win11 | Yes | Unsupported nesting, shared WSL lifecycle |

HCS is the real "VM from JSON" API on Windows. It has first-class save-to-file and clone-from-template (`SaveType: "AsTemplate"`, `TemplateSystemId`), Plan9 and SMB shares, and per-VM hvsocket SDDL ([HCS schema](https://learn.microsoft.com/en-us/virtualization/api/hcs/schemareference)). But Microsoft documents that **only Administrators or members of Hyper-V Administrators may call it** ([HCS error codes](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hcshresult)). That is why WSL works through the privileged `wslservice.exe` ([WSLC deep dive](https://devblogs.microsoft.com/commandline/?p=11811)). It is also why Podman 6 added a one-time elevated `hyperv-prep` that adds the user to that group ([Podman docs](https://docs.podman.io/en/latest/markdown/podman-system-hyperv-prep.1.html)), and why Claude Cowork users on Windows hit `HCS operation failed ... 0x80070005` ([claude-code#39285](https://github.com/anthropics/claude-code/issues/39285)). Either fix weakens Orole's posture. Group membership gives the interactive user full control of every VM and disk on the machine. A SYSTEM broker adds a privileged component to the trust boundary, which Orole has so far deliberately avoided.

WHP turns the model around. `WinHvPlatform.dll` lets the calling process own guest memory (`WHvMapGpaRange` on its own `VirtualAlloc`'d pages) and run vCPUs on its own threads ([WHP API](https://learn.microsoft.com/en-us/virtualization/api/hypervisor-platform/hypervisor-platform)). The VMM is therefore an **ordinary per-user process** that the daemon can start inside its existing job object. That keeps the honest-persistence rule intact: VMs die with the daemon, as agents already do. The research found no Microsoft statement that WHP calls need no elevation. QEMU, Docker `sbx` and microsandbox users all rely on it, though, and every one of them asks only for the one-time `HypervisorPlatform` feature enable, which works on Home as well as Pro ([QEMU WHPX](https://www.qemu.org/docs/master/system/whpx.html); [Docker sbx install](https://docs.docker.com/ai/sandboxes/install/); [microsandbox Windows](https://docs.microsandbox.dev/troubleshooting/windows)). QEMU WHPX is upstream and covers x86_64 from Windows 10 2004. It has known rough edges. MMIO-heavy legacy devices are slow, so use `-M q35,pic=off` with UEFI or direct kernel boot, plus virtio devices. `-accel whpx,ssd=off` gives a significant MMIO speedup, and a "Unexpected VP exit code 4" boot bug is still open ([QEMU WHPX docs](https://www.qemu.org/docs/master/system/whpx.html); [QEMU issue 4385](https://gitlab.com/qemu-project/qemu/-/work_items/4385)). OpenVMM is Microsoft's Rust single-binary VMM on WHP, with virtio-fs, virtio-net and Linux direct boot. Its "management interfaces continue to evolve" and development focuses on OpenHCL ([OpenVMM guide](https://openvmm.dev/guide/user_guide/openvmm.html)), so it is a candidate to watch rather than to build on.

WSL containers are the most important 2026 development and should be Orole's second VM backend. WSLC went GA on 29 September 2026 in WSL 3.0.1. Its C SDK (`wslcsdk.dll`) can be called from Go without cgo. It has a session → container → process model with stdin/stdout handles, CPU and memory caps, and per-session VHDs. Sessions are owned by a per-user `wslcsession.exe`, and Consommé user-mode networking routes guest traffic through a Windows process running as the user ([WSL API reference](https://wsl.dev/api-reference/); [WSLC deep dive](https://devblogs.microsoft.com/commandline/?p=11811)). A hands-on test showed **each session as its own VM**, with a ~706 MB idle working set, 2.8–5.9 s warm starts and a 34 s cold start, all measured nested under Proxmox and therefore inflated ([ComputingForGeeks](https://computingforgeeks.com/?p=172378)). The case against making it first is narrow but real. Microsoft has not stated the one-VM-per-session property. WSLC has no snapshot API. Its minimum Windows build is undocumented, so it may not run on 22000 at all. Enterprises can switch it off through Intune ([SmartScope](https://smartscope.blog/en/blog/wsl-containers-public-preview-2026/)).

Two third-party runtimes already deliver "WHP microVM per agent". **Docker Sandboxes (`sbx`)** gives each agent a microVM with a private Docker daemon on WHP. It adds a host-side policy proxy and sentinel credentials, needs Windows 11 x64, and is free locally ([Docker sbx architecture](https://docs.docker.com/ai/sandboxes/architecture/); [Docker Sandboxes docs](https://docs.docker.com/ai/sandboxes.md)). Its VMM is closed, though, and the research found no terms covering embedding or third-party control. **microsandbox** runs libkrun on WHP and ships a Go SDK, OCI images, snapshot and live fork, and egress allowlists. It is Apache-2.0, but labelled beta with Windows in preview, and the docs, PyPI and README disagree about how ready Windows is ([microsandbox changelog](https://docs.microsandbox.dev/changelog/2026-06-26); [PyPI](https://pypi.org/project/microsandbox/0.6.17/)). libkrun also warns that guest and VMM "pertain to the same security context" ([libkrun README](https://github.com/containers/libkrun)). Both deserve a spike. Neither should be the foundation of a security feature Orole has to stand behind.

## Process sandboxes are the fast first tier, but only VMs isolate a browser

Most code-task risk is a CLI writing outside its worktree, reading `%USERPROFILE%` secrets or exfiltrating over the network. Host process containment addresses much of that without a VM, and it keeps native Windows toolchains working. Tool compatibility is the real cost of moving a Windows user's project into a Linux guest. The Windows options split cleanly by build, and **build 22000 sits on the wrong side of the split**.

Microsoft Execution Containers (MXC) went GA on 7 October 2026. It is an MIT-licensed, policy-JSON containment layer with process, session, WSL-container and experimental microVM backends, plus a Learning mode that records denials ([Windows Developer Blog](https://blogs.windows.com/windowsdeveloper/2026/10/07/microsoft-execution-containers-policy-driven-containment-for-ai-agents/)). Its strong tier is the new PSEC/BaseContainer OS API. PSEC applies per-container WFP egress filters and a WinHTTP proxy "with no UAC prompt per launch", but it **requires 24H2/25H2 build .9278 or newer**, and **22000 is not listed** ([MXC os-version-support](https://github.com/microsoft/mxc/blob/main/docs/backends/process-container/os-version-support.md); [MXC networking](https://github.com/microsoft/mxc/blob/main/docs/backends/process-container/networking.md)). On older builds MXC falls back to AppContainer plus temporary host-DACL mutation. That fallback needs admin host prep just for `cmd`, PowerShell and `node` to start, because they fail access checks on `C:\` and `\Device\Null` ([MXC host-prep](https://github.com/microsoft/mxc/blob/main/docs/backends/process-container/host-prep.md)). A Go daemon can drive MXC without bindings by passing JSON to `wxc-exec.exe` ([microsoft/mxc](https://github.com/microsoft/mxc)). Codex already prefers MXC wherever it is available ([Codex Windows sandbox docs](https://learn.chatgpt.com/docs/windows/windows-sandbox)).

On 22000, the no-admin baseline comes from Codex's unelevated design. It uses a `WRITE_RESTRICTED` token with synthetic per-workspace capability SIDs, ACL grants on the workspace, a private desktop, and job-object limits ([token.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/token.rs); [cap.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/cap.rs)). It reliably blocks writes and keeps the process tree killable. It **does not stop reads or network exfiltration**, and Everyone-writable folders escape it ([Codex docs](https://learn.chatgpt.com/docs/windows/windows-sandbox)). Real read denial and egress control on pre-24H2 Windows need the "admin-once" recipe that Codex's elevated mode and Anthropic's sandbox-runtime arrived at independently. A one-time UAC step creates a dedicated local sandbox user, plus persistent WFP filters keyed on that user's SID that allow only loopback to a proxy port. After that, launches need no admin ([sandbox-runtime README](https://github.com/anthropic-experimental/sandbox-runtime); [Codex wfp.rs](https://github.com/openai/codex/blob/main/codex-rs/windows-sandbox-rs/src/wfp.rs)). Its field failures are documented: logon-right error 1385, antivirus blocking `CreateProcessAsUserW`, per-user tool installs the sandbox account cannot read, and DNS still resolving through Dnscache ([Vaughan summary of OpenAI's post](https://codex.danielvaughan.com/2026/05/14/codex-cli-windows-sandbox-engineering-restricted-tokens-acls-elevated-architecture/)). Standard users cannot add WFP filters at all, since Everyone holds only open and classify rights ([WFP access control](https://learn.microsoft.com/en-us/windows/win32/fwp/access-control)). That makes network enforcement on 22000 an install-time decision.

Process tiers fall short on the browser. Chromium is itself a broker/target sandbox that needs to spawn children, create desktops and manage jobs ([Chromium sandbox design](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/design/sandbox.md)). The research found no authoritative report of headless Chrome working inside an AppContainer or a write-restricted token. Prompt injection through browsed content is also the threat no vendor claims to have solved. Anthropic reports about 1% attack success under an adaptive attacker and calls that "meaningful risk" ([Anthropic](https://anthropic.com/research/prompt-injection-defenses)). UW researchers showed that the same-origin policy in agentic browsers reduces to the agent's injection defenses ([UW](https://agent-security.cs.washington.edu/agentic_browsers_sop.html)). An agent browser with its own profile belongs inside a hardware VM, which is the conclusion every hosted "own computer" product has reached: Manus and Devin Outposts on E2B Firecracker, Cursor on Firecracker microVMs, and E2B Desktop on Xfce with VNC ([E2B/Manus](https://www.e2b.dev/blog/how-manus-uses-e2b-to-provide-agents-with-virtual-computers); [Cursor](https://cursor.com/docs/cloud-agent); [e2b-dev/desktop](https://github.com/e2b-dev/desktop)).

## The recommended design: an envd-style guest on WHP, wired through pipes, with no NIC

The guest should be a small Debian-slim Linux image with a shell, Python, Node and Chromium. Debian beats Alpine here because Playwright effectively needs glibc ([zenn.dev](https://zenn.dev/dozo/articles/80e1ede2d1be05)). It boots from a read-only base image with a per-agent qcow2 overlay. Inside runs Orole's own Go guest agent, modelled on E2B's envd. envd is a Go binary with streaming process RPCs (`Start`, reattach by tag via `Connect`, resize via `Update`, `SendInput`, `SendSignal`), a file API, and pre-pause `/freeze` and post-resume `/init` hooks. It also reserves `min(MemTotal/8, 128 MiB)` so the agent survives a runaway tab ([process.proto](https://raw.githubusercontent.com/e2b-dev/infra/main/packages/envd/spec/process/process.proto); [envd main.go](https://raw.githubusercontent.com/e2b-dev/infra/main/packages/envd/main.go)). Every serious product uses this in-guest-daemon shape: E2B envd, Daytona's toolbox, OpenHands' agent-server, and Cua's computer-server ([OpenHands](https://docs.openhands.dev/sdk/arch/overview); [Cua](https://cua.ai/computer-sdk/computer-server)). Orole differs in transport. The others serve HTTP on a guest port because they are reached over a network. Orole's agent should serve one multiplexed stream on a virtio-serial or vsock device. On the QEMU backend, back that device with a **named pipe carrying the user-only DACL Orole already uses for the daemon**. QEMU's named-pipe chardev support is prior knowledge, not verified in this research, so the Phase 2 spike must confirm it. On Hyper-V-partition backends (HCS, WSL), the equivalent is guest-listens/host-dials over AF_VSOCK/AF_HYPERV through `go-winio` and `mdlayher/vsock`. That direction needs no HKLM service registration ([Microsoft hvsocket guide](https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/user-guide/make-integration-service); [OCaml hvsock README](https://ocaml.org/p/hvsock/1.0.2/README.md.html)). A per-VM token sent as the first frame still guards against other guest processes, because any guest process can open vsock. Give video its own stream so screencast frames never block keystrokes.

Networking should copy sandbox-runtime and Docker `sbx`, adapted to Orole's no-listener rule. The VM gets **no virtual NIC**. A tiny in-guest HTTP CONNECT/SOCKS5 forwarder on guest loopback is exported through `HTTP(S)_PROXY` and Chrome's `--proxy-server`, and it tunnels every connection over the control channel to a policy proxy inside the daemon. The daemon resolves DNS itself, enforces a per-sandbox allowlist through `policy`, and refuses private, loopback and link-local destinations after resolution. The existing public-address-only dialer in `fetch_url` already does exactly this ([fetch.go](../internal/chat/tools/fetch.go)). With no NIC, the guest has no route to the LAN, host services or metadata addresses, and **no DNS exfiltration channel**. That closes the gap sandbox-runtime still documents on Windows ([sandbox-runtime README](https://github.com/anthropic-experimental/sandbox-runtime)). Chrome falls back from QUIC to TCP when UDP is unavailable, so browser traffic goes through the proxy as well. The proxy can also implement credential sentinels, as `sbx` and Claude Code do: the guest sees a placeholder, and the daemon swaps in the Credential Manager value only toward approved hosts ([Docker sbx architecture](https://docs.docker.com/ai/sandboxes/architecture/); [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). This also answers an open repo gap. Copying host CLI tokens into a guest would break the credentials rule ([cli-runtimes.md](../docs/architecture/cli-runtimes.md)), so guest harnesses either sign in on their own or use proxied sentinels.

The browser runs headful Chromium on Xvfb or the `cage` kiosk compositor inside the guest. The guest agent launches it with `--remote-debugging-pipe` and a per-agent `--user-data-dir`, which Chrome 136 requires for remote debugging anyway ([Chrome blog](https://developer.chrome.com/blog/remote-debugging-port)). CDP never touches a TCP port. The human live view uses CDP `Page.startScreencast` JPEG frames with ack-based backpressure (`maxFramesInFlight`), relayed by the daemon over existing IPC events to a `<canvas>`. Each frame fits easily inside the 4 MiB IPC frame cap ([devtools-protocol Page.pdl](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Page.pdl)). Takeover becomes CDP `Input.dispatch*` calls gated by a Go-side "human has control" lock that pauses the agent loop. Logins happen in takeover, as ChatGPT agent does. A full-desktop view can come later: run x11vnc in the guest and hand noVNC a WebSocket-like shim over IPC. noVNC officially accepts a `WebSocket` or `RTCDataChannel` object instead of a URL ([noVNC API](https://github.com/novnc/noVNC/blob/master/docs/API.md)), but whether a duck-typed shim works is unverified. WebRTC streamers such as neko need exposed UDP/ICE ports, and "reverse proxies cannot forward WebRTC" ([neko docs](https://neko.m1k1o.net/docs/v3/configuration/webrtc)), so they are out.

Files should live on the VM's own disk. Shared folders are slow and dangerous. WSL's 9p measured about 58x slower per small-file operation than ext4 ([brainwagon](https://brainwagon.org/blog/2026_07_11_wsl2_filesystem_speed)). virtiofs on a Windows QEMU host is unverified, and a share is a large attack surface into the host. Copy repos in and export changes out through the guest agent's file RPC. This is Docker's "clone mode" ([Docker sbx architecture](https://docs.docker.com/ai/sandboxes/architecture/)). Changes come back as a patch applied to the session's host worktree, so Orole's existing diff and review keep working unchanged. Today they refuse non-local sessions ([manager.go](../internal/agents/manager.go)). Read-only host folders are reserved for an explicit, Go-approved grant served by a host-side file server that enforces the read-only rule itself.

For sizing, the per-VM budget is an estimate: 100–200 MB for kernel and agent, 50–100 MB for display and VNC, and 200 MB to over 1 GB for Chromium. One headless measurement saw about 180 MB idle and 940 MB peak on Amazon.com ([PyBA](https://pyba.readthedocs.io/en/latest/performance.html)). Plan on a 2 GiB cap per browser VM. By that reasoning, a 16 GB laptop runs four or five active browser agents and a 32 GB laptop ten to fourteen, with idle VMs suspended. Treat these as hypotheses to measure. No published number exists for small-VM boot or save/restore on WHP, and Firecracker's sub-second figures do not transfer.

## The phased plan maps onto seams that already exist

Every integration point except the hypervisor glue is already an interface, so most of the work is new implementations rather than refactoring. The one structural change is in `internal/agents`. It branches on `localMachine(...)` in Start, launch, restart, diff, attachments and worktrees ([manager.go](../internal/agents/manager.go); [options.go](../internal/agents/options.go)). Replace that binary branch with a `Location` interface (local, ssh, sandbox) before adding the third case.

| Seam | Existing interface | Sandbox implementation |
|---|---|---|
| Lifecycle and IPC | `svc_<name>.go` + `handle[P,R]` ([daemon.md](../docs/architecture/daemon.md)) | `internal/sandbox` (Manager, Store, `Hypervisor` interface) + `svc_sandbox.go`, `sandbox.*` methods, `sandbox.changed` events; `app.Sandboxes` bridge, then `go tool mygo generate` |
| Persistence | numbered forward-only migrations | `0112_sandboxes.sql`: sandbox rows keyed to `machines.id`, plus a `sandbox_id` column on agent sessions |
| Identity and UI chips | `machines.Machine{Kind, Transport, Backend}` ([machines.go](../internal/machines/machines.go)) | `kind=sandbox`, `transport=pipe|hvsock`, daemon-generated identity; footer and "Run on" picker reuse `boxes.ts` |
| Code tasks | `agents.Adapter`/`Process`/`Host`, `pipeProc` over `io.Reader`/`Writer` ([adapter.go](../internal/agents/adapter.go)) | `Location` for sandbox: structured `claude -p --output-format stream-json` / `codex app-server` over guest-agent streams, so approvals stay structured rather than remote `process` mode |
| Terminals | `terminals.Backend`/`Process{Read, Write, Resize, Wait}` ([terminals.go](../internal/terminals/terminals.go)) | guest-PTY `Process`; per-session backend routing (the manager holds one backend today); owner `sandbox:<id>` |
| Files | `files.Provider` + `Registry.Register` ([files.go](../internal/files/files.go)) | `sandbox` provider, namespace `/<sandbox-id>/<path>`, backed by guest file RPC |
| Policy | `policy.Check` actor/action/resource/effect ([policy.go](../internal/policy/policy.go)) | `sandbox.create|start|exec` (write), `sandbox.destroy|network|mount` (destructive), resource `sandbox/<id>`; bots flow through the existing auto-approve hook and inline approval cards |
| MCP and skills | `gateway.Backend`; gateway "never" reaches remote machines ([gateway.go](../internal/agents/gateway.go)) | host-side `orole-daemon mcp-gateway` per session, its stdio relayed into the guest; actor stays `agent:<sessionID>` |
| Bot tools | `chat.Tool` registered in `registerChatTools` ([svc_chat_tools.go](../internal/daemon/svc_chat_tools.go)) | `sandbox_shell`, `sandbox_browser` (navigate, snapshot, click, type, screenshot); results fenced untrusted |

**Phase 0: decide and prepare (1–2 weeks).** Write ADR 0008. It should accept a one-time elevated setup helper that is never the daemon, choose a Linux guest, and define per-task ephemeral sandboxes by default with named persistent sandboxes per bot as opt-in. Add `internal/sandbox` with `NotImplemented` backends and a setup screen that detects WHP and WSL state without admin, per the no-mock-data rule ([AGENTS.md](../AGENTS.md)). Do the `Location` refactor in `agents`. Also put a 24H2/25H2 machine or VM next to the 22000 box. 21H2 has had no security fixes since 2023-10-10 ([Microsoft lifecycle](https://learn.microsoft.com/en-us/lifecycle/announcements/windows-11-21h2-end-of-servicing)), and it cannot test MXC/PSEC, WSL mirrored networking, the `wsb` CLI or likely WSLC.

**Phase 1: host containment for code tasks (works on 22000).** In the existing launch path in `adapter.go` and `job_windows.go`, add job-object memory, CPU and process limits, a write-restricted token with a per-session synthetic SID ACL'd onto the worktree, a private desktop, `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, and an environment allowlist modelled on the automation runner's ([command.go](../internal/automations/command.go)). `x/sys/windows` lacks the AppContainer and restricted-token declarations, so declare them through `NewLazySystemDLL` ([golang/sys](https://github.com/golang/sys/blob/master/windows/types_windows.go)). Offer an optional "hardened mode" through the elevated helper: a sandbox user plus SID-scoped WFP. Add an MXC backend through `wxc-exec.exe` on builds that support PSEC. Surface a setting such as "Run Yolo tasks only in a sandbox". The UI must state what this tier does not stop. Phase 1 must not route traffic through a loopback proxy listener unless that listener is justified as an exception, as the OAuth callback is ([security-permissions.md](../docs/architecture/security-permissions.md)). The VM tier needs no such listener.

**Phase 2: the Linux agent VM on WHP.** Bundle QEMU, which carries GPL obligations to review, together with a reproducible Debian-slim image, a base-plus-qcow2-overlay disk layout, and the Go guest agent. The elevated helper gains a `HypervisorPlatform` enable step. Wire up the pipe channel, the guest-PTY terminal `Process`, the `sandbox` files provider, the NIC-less egress proxy, the gateway relay, and the code-task `Location` with patch export back into the host worktree. Run QEMU inside the daemon's job object so the existing honest-persistence statement holds: running processes survive GUI restarts but not daemon exit; disks survive reboots. Spike microsandbox and Docker `sbx` against the same guest-agent contract during this phase, and measure boot time, idle RAM and stability on real hardware.

**Phase 3: browser and bots.** Add Chromium over `--remote-debugging-pipe` behind the guest agent. Expose `sandbox_browser` as a bot `chat.Tool` and a gateway MCP tool. Build the screencast live view and takeover lock in the task view's session rail, and a per-bot persistent "computer" with its own profile. Disable Chrome DevTools MCP telemetry and CrUX if it is used ([chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp)). Consequential browser actions get Go-side confirmation.

**Phase 4: lifecycle and more backends.** Add a warm pool of one or two pre-booted VMs, then idle suspend. Disk snapshots come before memory snapshots, because the whole industry treats memory snapshots as "premium and fragile". E2B pauses at about 4 s per GiB, Fly checkpoints rewind files only, and a Go guest daemon crashed after Firecracker restore until a quiesce hook was added ([E2B persistence](https://docs.e2b.dev/sandbox/persistence); [Fly Sprites](https://fly.io/sprites/checkpoint-restore.md); [wrenn](https://git.omukk.dev/wrenn/sandbox/pulls/2)). Never snapshot while secrets are present. Reseed RNG and regenerate tokens and machine-id on every clone. Add reconcile-on-start GC and disk quotas. Then add WSLC as a second backend once it is verified on supported builds, an HCS backend only if a SYSTEM broker is later accepted for clone-from-template speed, and optional detection of a user-installed `sbx`.

## Conclusion

The question "something like Firecracker, but local on Windows" carries a hidden premise: that the VMM is the hard part. Docker, E2B and Microsoft's own WSLC team have each shown it is not. The hard parts are the control channel, the egress proxy, credential handling and lifecycle semantics. Orole already owns the equivalents of all four: the authenticated pipe, the SSRF-guarded dialer, Credential Manager and honest-persistence rules. That makes the VMM a swappable backend. WHP lets that backend run unprivileged inside the daemon's own process tree, the one place Orole's architecture says agents belong. Building on WHP rather than HCS or nested KVM keeps the security story unchanged: no new privileged service, no network listener, and a VM that dies with the daemon.

The main uncertainty is empirical. No one has published WHP small-VM boot, RAM or restore numbers, WSLC's per-session VM and 21H2 support are unconfirmed, and MXC's GA maturity is untested. Phase 2's spike should therefore be judged on measurements from real hardware, not vendor claims. The 37% cold-start success rate measured against one vendor's sub-90 ms marketing shows why ([MarkTechPost via search snippet](https://www.marktechpost.com/2026/08/27/best-agent-sandboxes-2026-cold-start-pricing-network-policy/)). Strategically, Windows is converging on MXC and WSLC within about a year. Orole's durable asset is a single policy object and guest-agent contract that translates to whichever backend a given machine supports. Its first real users will be on 24H2+, so the 22000 development box should be upgraded or supplemented before Phase 1 ships.
