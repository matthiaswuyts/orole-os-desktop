# Frontend component structure

`frontend/`: Vite, React, TypeScript strict, Tailwind v4, Zustand. The UI kit is Shipyard's coss/Base UI
components, copied (see `docs/research/upstream-attribution.md`). Look and density follow Shipyard.

```
frontend/src/
  main.tsx, App.tsx          mount, theme application, shell
  components/
    ui/                      coss/Base UI primitives (button, dialog, menu, switch, table, ...)
    shell/                   AppShell, Sidebar, SidebarProjects, StatusBar, CommandPalette, Logo
    widgets/                 Widget, WidgetGrid, registry.tsx (widget registry), builtin.tsx
    ascii/                   AsciiBackground.tsx (one canvas band per window), motion.test.ts
  features/                  one directory per view
    registry.tsx             ViewId -> lazy component; a view missing here renders NotImplemented
    home/ projects/ tasks/ skills/ mcp/ images/ settings/ shared/ (States.tsx: NeedsDesktop, NotConnected, NotImplemented)
  stores/                    Zustand: daemon (link + health polling), settings, ui (ViewId, focus), workspaces, projects
  lib/                       backend.ts (inDesktop), nav.ts, commands.ts (palette registry), coreCommands.tsx, utils.ts, diff.ts, projects.ts
  themes/                    builtin.ts (shared theme/terminal palette registry), custom.ts (validated custom tokens), themes.css
  mygo.ts                    GENERATED by `go tool mygo generate` from internal/app; commit it
```

## Conventions

- **One token layer**: `index.css` + `themes/themes.css`. No per-component colour constants.
- **Add a view**: create `features/<name>/`, add one line to `features/registry.tsx`. Nav ids live in `lib/nav.ts`
  and `stores/ui.ts` (`ViewId`).
- **Add a command**: `registerCommands` / `registerProvider` in `lib/commands.ts`.
- **Add a widget**: register in `components/widgets/registry.tsx`.
- **Add a setting section**: `features/settings/SettingsView.tsx` `SECTIONS` (`built: true` once rendered).
- **Settings window**: the sidebar Settings button calls `Desktop.openSettings(section)` (`internal/app/applications.go`),
  which opens (or focuses and re-targets via the `settings-window:section` event) one native window loading
  `/?window=settings&section=…`. `App.tsx` renders `features/settings/SettingsWindow.tsx` there: a title bar plus
  `SettingsView` only (settings sidebar and pages), no app shell. The window keeps its own Zustand stores and loads
  settings, workspaces and daemon polling itself; settings changes propagate via the existing `settings:changed`
  event. In the browser preview (no native windows) the button keeps switching the in-app Settings view. Other
  entry points (palette, deep links, status-bar MCP button) still use the in-app view.
- **Backend access** goes through generated bindings (`Daemon`, `Settings`, `Workspaces`, `Terminals`, `Projects`,
  `Git`, `Worktrees`, `System`, and `events`). `lib/backend.ts` `inDesktop` is false in a plain browser; then
  the app is a **preview**: only UI preferences persist (localStorage), integrations show setup states, views that
  need the daemon show `NeedsDesktop`. No mock data in production paths.
- **ASCII art** uses one animated canvas per window (`AsciiBand`), never per widget; motion policy is `decideMotion`
  (disabled/static/paused/reduced-motion/unfocused/low-power/intensity). Settings renders cached, still PNG previews
  of the 11 real scenes using one temporary 480px canvas at a time, disconnected immediately after capture.
  `ascii.randomOnStartup` chooses a renderer-local `activeAsciiScene` once after the first successful settings load.
  Reloading settings, changing focus, or remounting Home does not reshuffle. Enabling the option applies next startup;
  selecting a preview immediately selects that scene and disables random mode. The saved manual scene is not overwritten
  by random outcomes. There is no timed slideshow. See `docs/research/ascii-library.md`.
- Settings > Diagnostics also renders `features/settings/Autostart.tsx` (start-at-login switch, credential store,
  WebView2, schema version, data dir, pipe, log tail) from `System.diagnostics()`.

- **Keyboard hints** use coss [`Kbd` / `KbdGroup`](https://coss.com/ui/docs/components/kbd):
  one key per keycap, grouped combinations, with accessible shortcut labels.
- **UI tooltips** use coss [`Tooltip`, `TooltipTrigger`, `TooltipPopup`](https://coss.com/ui/docs/components/tooltip)
  under the shell's shared provider. Compose triggers with `render` to retain their
  real element and handlers. Truncated text hints are keyboard focusable; disabled
  browser actions use a focusable span trigger. Do not use native `title` hints or
  reintroduce the removed custom `Tip` layer. Iframe titles and chart-data tooltips
  have separate purposes and remain unchanged.

Browser smoke verified grouped keycaps, hover and keyboard-focused sidebar hints,
the composed notification trigger, and keyboard access to the disabled
browser-action explanation. The rebuilt NSIS-installed WebView2 app displayed the
keycaps and sidebar tooltip; its runtime error buffer was empty.

## Shell and themes

`App.tsx` starts its existing settings/workspace loads, daemon polling and task subscriptions
while `components/shell/StartupScreen.tsx` gates the shell. The centered ASCII bar follows
the classic `[====>   ]` style from [ascii.rest/progress-bar](https://ascii.rest/progress-bar/),
but uses actual settled startup checks, not the upstream demo's timed simulated percentages.
Preferences, workspaces, tasks and the first daemon connection result each account for 25%.
Failed requests count as checked and retain their store errors; offline startup can reach the app.
Preview mode skips daemon/task work through the existing preview states. The real 100% state
paints before handoff, without a minimum-duration timer. Once opened, subsequent refreshes
or disconnects do not restore the screen. Native navigation remains mounted during startup.
The bar exposes a named ARIA progressbar and live status; it has no looping motion.

The sidebar begins at the workspace switcher without a top spacer. `AppShell` owns
the route heading; feature toolbars keep their actions, counts and filters without
repeating it. Detail headings and Settings subsection headings remain.

`BUILTIN_THEMES` supplies Settings, onboarding, command-palette actions and terminal
colors. Available palettes: Orole Midnight, Obsidian and Light; Solarized Dark and
Light; Catppuccin Latte, Frappé, Macchiato and Mocha. Saved IDs are stable settings
values. Applying a palette clears previous built-in tokens; custom themes layer
validated overrides over Midnight. Terminal colors update without restarting sessions.

Installed WebView2 smoke exercised all six added palettes, checked light/dark color
schemes, daemon-backed persistence and reload, keyboard command-palette switching,
zero sidebar top padding and a single Agent Dashboard route heading. A mounted
PowerShell terminal recolored between Solarized Light and Catppuccin Mocha while
retaining PID 2340.

## Workspaces

The workspace menu opens Settings > Workspaces for real create, rename, switch,
and confirmed deletion controls. At least one workspace is retained. Desktop
mutations use the daemon's `Workspaces` service; preview mutations use localStorage.
Each workspace has its own debounce timer, and all saves/deletes are serialized
so switching cannot lose an edit or let an in-flight save recreate a deleted
workspace. Renaming clears the older pending-name snapshot before saving.
Browser smoke verified create, rename, and deletion across reloads; the rendered
management surface had zero automated axe violations. Regression tests cover
rapid switches, delayed saves, and deletion during an in-flight save.

## Sound feedback

`lib/audio.ts` owns one `@web-kits/audio` engine. `shell/AudioFeedback.tsx`
maps semantic activations to brief synthesized cues; no hover or typing sounds.
Settings > Customization > Sounds persists interface enablement and web volume; there is no test-interface-sound action. A zero volume,
unfocused/hidden window, missing user activation, or stale asynchronous activation
prevents playback. Losing focus stops voices and suspends the engine.
In-app notification cues use the source preference and only new events explicitly
marked `sound && !native`; native delivery never also plays a web notification cue.
Windows owns native-notification volume and may suppress delivery.

Browser smoke exercised real Web Audio playback, keyboard slider changes, mute,
and volume persistence after reload. The Sounds surface had zero automated axe
violations. These checks do not prove acoustic audibility or Windows toast delivery.

The installed Windows desktop's Test notification action persisted a real
`system.test` notification and reported Windows acceptance through MyGo, both with
sound enabled and disabled. The per-source silent preference survived a native
page reload. OS display and acoustic audibility remain dependent on notification
permissions, volume, and Focus Assist; API acceptance is not evidence of either.

## Alerts & automations settings

Settings groups this surface into **Alerts** and **Automation limits**, retaining the existing navigation IDs.
Alerts aligns per-source Allow, Windows, and Sound controls, marks default versus custom preferences, and offers Reset.
Delivery details are collapsed; errors, connection recovery, saving status, and the real notification test remain visible.
Automation limits separates concurrency controls from local webhooks. Port and signing instructions are under connection
details; credential generation and explicit replacement confirmation remain available. Drafts survive save failures,
and offline state prevents mutations while still allowing cancellation of secret replacement.

Headless verification covers startup scene stability/manual override, alert preferences and disabled actions,
automation save recovery and secret confirmation. All 11 real scene first frames were generated successfully.
These checks do not verify browser canvas snapshots or visual layout.

## Home composer and monitoring

Home shows the new-task composer directly, without a tab switcher or running-task
list. Task status and history live in the Tasks dashboard and project task lists.

`HomeAgentComposer` is one coss InputGroup: prompt, assistant-ui attachment chips and
the entire launch toolbar share the input surface. It is centered and capped at 720px,
with an opaque card background in both themes and while disabled. There is no New task
badge or keyboard-hint footer. Project selection includes Create new project without
losing the draft. System choices use real box names/status and scope available projects.
Worktree choices include a new isolated worktree, current checkout and existing
registered worktrees. Folderless projects use their managed workspace.
The permission mode (Manual, Auto or YOLO) sits beside the worktree menu; a mode the selected agent cannot run
falls back to Manual.

`AgentModelPicker` uses a compact provider-logo/model/effort trigger (for example,
Opus 5.5 · X-High), with searchable provider and model pages in one popover.
`model-options.ts` formats labels without rewriting the actual model selectors.
The beui-derived `RangeSlider` exposes only daemon-reported reasoning levels;
Auto leaves the harness override unset. Keyboard control, reduced motion and
accessible effort labels are supported. Home saves model and effort independently
per provider in local UI preferences, immediately on selection, and restores them
when switching providers/systems or reopening the composer. An explicit Auto choice
is saved too. Missing models fall back to the discovered default; unsupported effort
is omitted from launch without erasing the saved preference, so returning to a
compatible model restores it. Missing catalogs are explicit, not fabricated.
Start or Enter calls `Agents.start`; Shift+Enter still inserts a newline.
Duplicate submissions are blocked and uncertain retries reuse their request key.

Files can be selected, dropped or pasted. `useTaskAttachments` uploads through
`Agents.uploadAttachment`, shows real pending/error/ready state, and prevents launch
while an attachment is incomplete. Removing a pending chip discards any upload that
finishes later. A failed start preserves both draft and attachments. Limits are
8 files per task and 2 MiB per file, enforced again by the daemon within the 4 MiB IPC
frame budget. Attachment-only tasks are allowed.

The daemon stages opaque IDs under `OROLE_HOME/attachment-uploads`; abandoned staging
expires after 24 hours. At launch it copies files into an exclusive
`.orole-attachments-<session UUID>` directory inside the selected workspace/worktree.
A self-ignoring `.gitignore` is installed before input bytes, keeping normal review
and `git add --all` from publishing them (not a protection against `git add --force`).
The actual task prompt includes file references for the harness's file/image tools;
this is file handoff, not fabricated native multimodal-message support. Session inputs
remain for restart independently of discarded staging uploads. Remote transfers use
the existing pinned, root-checked, authorized SFTP path and fail before agent dispatch
if directory creation or file transfer fails.

An isolated real-daemon IPC smoke uploaded a file, launched a process that read the
actual prompt's file reference, verified exact contents, retried after staging disposal
without duplication, and checked Git exclusion. No paid model call, external SSH
handoff, browser visual check or development server was used for this verification.

Local execution uses structured harnesses. Configured remote boxes use their advertised
process-mode capabilities and approved directories; unavailable capabilities remain
unselectable. Remote execution uses the remote harness configuration, not the local
skills/MCP gateway, and the composer states this limitation.

Notifications live at the right end of the window header, separated from native
window controls by a vertical divider and MyGo's reserved caption-button inset.
The sidebar toggle sits beside the workspace selector; Settings has no status dot.
Daemon status remains available in the footer.

The rebuilt NSIS-installed WebView2 UI exercised harness/model submenus,
working-directory entry, pointer and keyboard reasoning selection, and the
separate daemon approval. Codex launched with `gpt-6-astra` and `low` reasoning
and returned the requested `4` in its terminal; the smoke session was then stopped.
Keyboard activation of Adjust effort focuses the range input after the menu's
own focus update. The coss slider forwards its accessible name and value text to
that input. Header notifications opened with the sidebar hidden; the native
caption inset measured 138 px. The final runtime error buffer was empty, and an
860 px browser viewport had no document or composer overflow.

`features/system/HostActivity.tsx` uses Dither Kit area/line charts only. Host CPU
and physical memory come from daemon-owned OS sampling, separately from daemon
heap. Histories contain at most 60 real samples, with accessible history tables;
unknown intervals are not fabricated. Sampling pauses while hidden, unfocused,
or outside the viewport. Charts disable animation and bloom.

Installed-desktop smoke displayed real CPU and memory histories, disk capacity,
and host uptime; losing focus displayed the paused state. The footer uses the same
machine health source, custom box names, and coss Preview Card/Tooltip controls.
Updates appear only after MyGo confirms a newer signed release; unsigned builds
show their limitation in Settings, not a fake update action.

## Unified search

The globally mounted command palette registers commands, projects, repositories,
approved local/project files, remote files, GitHub issues/PRs, agents, terminals,
settings, Mail, and Drive. Remote files, Mail, and Drive require explicit provider
selection; All does not initiate their sensitive searches. Existing authenticated
domain APIs provide bounded results without indexing private content or forwarding
content between integrations.

Results use domain selection stores. Pending Mail-thread, Drive-file/folder and
terminal selections survive lazy view mounting. Missing terminals report an error,
not a newly created replacement shell. Provider failures remain visible alongside
successful results. Changed filters, shortened queries, and cancellation discard
stale responses. Cancellation does not undo already-issued daemon policy requests
because the existing generated bindings do not expose transport cancellation.

Browser smoke exercised the provider filters and an actual theme command; live
named-pipe smoke found Workspaces, Sounds and Plugins with exact settings-section
actions and observed no policy prompts from default search. Remote and live
Mail/Drive result navigation still requires configured external endpoints. The
desktop-required preview message names `go tool mygo dev`, not Vite-only startup.

## Skills and MCP servers

Settings > Skills and Settings > Integrations (connectors and MCP servers in one list) configure things once for every harness.

- `features/skills/SkillsView.tsx`: the central skill registry (`Skills.*`). Lists skills with search and an
  enable switch, edits `SKILL.md` (a new skill starts from `skillTemplate`; saving goes through the daemon,
  which validates the name and frontmatter), deletes with confirmation, imports skills discovered in harness
  folders, and shows per-harness sync state (installed, synced/outdated/missing counts, gateway entry) with
  Sync and Sync all. Skills reach every harness through the Orole MCP gateway and are synced to native folders.
  The list is metadata-only: opening an editor fetches the full body with `Skills.get(name)`. Only the latest
  open request may populate the editor; closing or starting a new draft discards pending results. The editor
  cannot save while a body is loading, and save completion cannot overwrite another selected draft.
- `features/integrations/Integrations.tsx`: Settings > Integrations, the one place to connect services. Rows come from
  `directory.ts` (official remote MCP servers plus the built-in GitHub integration) with company marks from the bundled
  simple-icons set (`BrandLogo`); Add registers the server (`MCP.add`, OAuth) and starts sign-in when it answers
  `auth_required` (`useConnect.ts`). "Custom connector" takes only a name and URL. Registered servers appear under
  Connected with Manage, which opens `features/mcp/ServerDetail.tsx`: logo, Reauthenticate/Sign in, Disconnect, tool chips (click to turn a tool off), server URL, and a closed Advanced section (OAuth client, per-tool permission levels, diagnostics). Directory
  entries must answer 401 with protected-resource metadata and offer dynamic client registration; servers needing a
  pre-registered client go through Custom connector and Manage. The old Settings > MCP section id still resolves here.
  Mail and Drive embed `MCPSettings` (adapter mode) in their setup screens.
  Configuration search, palette commands, onboarding links and the status-bar button open this section.
  The custom dialog form uses `display: contents` so its scrollable body and footer participate in the popup's
  flex layout and stay inside its rounded border.
Generated images remain available within task conversations. The separate Images page, gallery,
sidebar entry, composer shortcut, and deep link have been removed.

## Task view

`features/tasks/TaskView.tsx` is a chat-only agent session, without a tab strip or duplicate header.
`TaskHeader` replaces the generic page title in `AppShell` while a task is open: its bundled provider
logo and task title are the only task-specific titlebar content. Returning to the dashboard restores
its page title. The titlebar's command-palette plus button is removed; the keyboard shortcut remains.

`features/tasks/TaskView.tsx` wraps the real conversation and composer in `TaskCanvas`; file and
image selections open a responsive side canvas without removing chat.

- **Feed/navigation** (`Feed.tsx`, `RunEntries.tsx`, `lib/taskEvents.ts`): `chat_types.go` defines structured provider
  payloads; `taskChatTypes.ts` mirrors `Event.data` payloads not reachable through generated services.
  Feed items normalize provider events without inferring unsupported hierarchy, progress, citations, or
  context data. Search covers loaded transcript events only; loading older history remains available.
  Day boundaries use local calendar time and are the only dates in the feed; a row's exact time is only its
  hover `title`. Follow-scroll pauses when the reader leaves the end, retains the anchor when older pages
  prepend, and offers a return-to-latest control.
- **Runs** (`groupRuns` in `lib/taskEvents.ts`, `elements/run-activity.tsx`): the feed shows one entry per user
  message and one collapsed `RunActivity` per assistant turn (the events between two user messages). Reasoning,
  tool calls, sources, sub-agents, interim assistant messages, system notes and already-decided approvals fold into
  the run in recorded order; the closing assistant message(s) (those after the turn's last activity), reported
  files and images stay outside it. Pending approvals and questions, errors, policy notices and a failed turn's
  result go in the always-visible `attention` slot. The status row reads the live activity (`Working`), `Needs your input`,
  or `Worked for 2m 13s` (first to last event of the turn, omitted when under a second or unknown), with
  failed/stopped/incomplete variants. Open state is per run key, collapsed by default and preserved across updates;
  a search hit inside a collapsed run opens it. A turn with only a plain answer renders no run row.
- **Tool rows** (`lib/toolLabels.ts`, `elements/tool-timeline.tsx`): each step is `{verb, chip, icon}` in plain words:
  `Ran` + the real command with a PowerShell/cmd/bash wrapper stripped, `Searched the web` + the query (no chip when
  empty), `Read` + file name, `Edited` + files with +/- counts, `Searched files`, `Used <server> · <tool>`, otherwise a
  humanized name. A failed tool shows an explicit `Failed` state. The raw tool name, complete input and output sit behind
  the row's own disclosure (`ToolDetails`), never as primary text.
- **Activity/artifacts**: correlated tool call/results, policy decisions, questions/answers, provider
  child-agent state, real sources, files and image-generation stages appear only where the harness reports
  them. A running image generation shows the `ImageGeneration` element (dot grid, shimmering `Generating`,
  prompt); the real `TaskImage` replaces it once the artifact exists, and there is no regenerate control because
  no regenerate action exists. Questions and tool permissions have separate daemon APIs and lifecycles. Follow-up
  queue states are daemon-owned and durable; restart never replays ambiguous sends. Queue dispatch never launches an
  agent process.
- **Tool permissions** (`TaskApprovalCard`, `elements/permission-grant.tsx`, `lib/permissionLabels.ts`): a compact
  card in plain words: the capability (`Run a command`, `Edit files`, `Use <MCP server>`, `Access the network`...),
  the requesting agent, and the reach the approval would grant (the full command and folder, or the file paths, in
  scrollable wrapped monospace; never truncated). Only `Deny` and `Allow once` are offered, because the daemon request
  carries no wider grant; the decision still goes through `Agents.approve` and Go decides. Consent stays bound to
  the complete request snapshot (tool and exact `inputJSON`): a changed snapshot under the same ID starts over, and a
  request without its complete input cannot be approved. All text is untrusted, escaped (control and directional
  characters shown as `\uXXXX`) and rendered inert; the raw request is behind `Details`. A resolved request is one
  badge (`Allowed once` / `Denied`, plus a reason only when one exists).
- **Canvas/files** (`TaskCanvas.tsx`): reported files and generated images open from their corresponding
  feed cards. `Agents.taskFile` reads through an OS-rooted local workspace boundary. Previews are bounded,
  inert text/raster data; remote sessions do not receive local-file access.
- **Markdown** (`components/Markdown.tsx`, `react-markdown` + `remark-gfm`): agent text is untrusted.
  No raw HTML is parsed; images are local daemon-returned raster `data:` URLs, and links open only http(s)
  through `Shell.openExternal`. Code uses lazy CodeMirror/Lezer highlighting; unknown languages remain
  inert text.
- **Composer**: local structured follow-ups use `Agents.sendMessage`; the daemon selects immediate
  delivery, same-session continuation, or its durable follow-up queue. Staged attachments are copied
  before acceptance; queued messages retain their own model/effort selection until dispatch.
  Cancellation/resume and uncertain-delivery state remain explicit. Context shows nullable
  provider-reported measurements only, never an inferred token breakdown.
  The Code composer is one rounded surface (`InputGroup`): attachment chips and the draft on top, then a single
  toolbar. Left: attach and `PermissionModeSelect`; right: model/reasoning picker, dictation (`ComposerVoice compact quiet`),
  context ring and send. The folder, branch and "Local checkout" line sits quietly under the surface.
- **Permission modes**: `PermissionModeSelect` (Base UI Select) offers Manual, Auto and YOLO with a one-line description each.
  Auto reads "The agent decides which actions are safe"; where the harness has no such mode the option is badged
  Approximated with the daemon's explanation (`HarnessOption.permissionModes`). YOLO opens an AlertDialog explaining
  that no prompts will be shown and only then sends `confirmYolo`; the daemon enforces the confirmation, the
  `agents` setting that can turn YOLO off (Settings > System > Task permissions) and everything else. In a running task the
  choice calls `Agents.setPermissionMode`; the control is disabled with the daemon's reason (`followup.permissionModeReason`)
  for terminal, remote and read-only review sessions. Home reuses the control: the default is Manual, Auto is remembered in
  `localStorage` (`orole.task.permissionMode`), and YOLO never is.
  Optional dictation (`ComposerVoice`) records the microphone with `getUserMedia` + `MediaRecorder` (the packaged
  WebView2 has no speech service, so the Web Speech API is not used) and sends the recording to the daemon
  (`Dictation.transcribe`), which transcribes it with OpenAI using the user's own OpenAI API key. It requires an
  explicit consent disclosure that audio goes to OpenAI; without a connected key it shows a setup state that opens
  Settings > AI providers. Transcripts remain editable and are never sent automatically.
- **Harness limits**: installed Claude Code 2.1.289, Codex CLI 0.156.1, and Oh My Pi 18.8.4 protocols
  were inspected. Codex and OMP support typed question responses and authoritative context occupancy;
  Claude contributes only fields its stream actually reports. Sources are structured harness output,
  not URLs guessed from prose. Child-agent status and image-generation stages are provider-specific.
  Terminal/process sessions do not advertise these structured capabilities.
- **Publish** (Changes sheet, `PublishPanel`): commit message, Commit, Push branch, Open pull request (title, base, body,
  draft). Push and PR show a confirmation listing the branch, remote and PR title/base, then call `Agents.publish` with
  `confirmed: true`. The panel calls the daemon once per step (commit, push, PR) so progress and a failure are attributed
  to the real step; errors surface as toasts. It is disabled with a reason when the session has no branch or worktree.

## Navigation, projects and tasks

The sidebar offers Home, Tasks (view id `agents`), Review, Automations and Settings (`lib/nav.ts`,
`features/registry.tsx`). Skills and MCP live in separate Settings sections, retaining their full-page
editors and scrolling. Native deep links use `orole://open/settings/skills` and `orole://open/settings/mcp`;
the allowlist is in `internal/applications/navigation.go`. Under the rows, the
project tree expands each project to its **tasks**: dashboard-visible sessions associated by `Session.projectId`
on the same machine, newest first, with status dots and "Needs you" or "Failed" badges. Older sessions without
an ID still match their `Session.project` folder (`features/projects/tasks.ts`). Folderless projects offer
"Start a task" immediately; they use a persistent daemon-owned workspace, not a user-selected folder.
Worktrees are an implementation detail of a task; there is no worktree view. "Open tasks" filters the
Tasks dashboard (`useAgents.projectFilter`, shown as a clearable chip).
Project rows include a folder icon and named system badge. Task rows retain status,
show their execution system beside the title, and place the agent logo at the right edge.
The sidebar is 256px wide (capped at 45vw on narrow windows). Left-aligned titles take the flexible
space; system badges are capped at 64px and may shrink rather than squeezing titles.
Hover tooltips retain the full project/task name and system labels.

The **New task** page (`features/projects/NewTaskView.tsx`, view id `new-task`, not listed in the sidebar) replaces the old modal.
`useProjects.openNewTask(projectId?, prompt?)` records the project, prompt and the view to return to (`closeNewTask`, or Escape
once nothing is focused), then switches to the page; each opening is a fresh page (`newTask.seq`). It starts a task with
`Agents.start` through the same composer and launch state as Home (`HomeComposerView`, `useHomeTaskLaunch`): one `StartSpec`
with `projectId` and an empty `dir` (resolved by the daemon), the chosen harness, optional model and reasoning, the prompt,
attachments and the project/system/worktree menus. A retry of an identical spec reuses its idempotency key, so an uncertain
failure never starts a second agent. Errors appear as toasts. Above the input sit one small random ascii.rest piece
(`AsciiMark`, from a fixed list of 13 text pieces; hidden when the ASCII setting is off, still when motion is reduced), the
project name and its repository, system and folder. Below it: "New <agent>" rows that choose the agent and focus the input,
"All tasks in <project>", and "Pick up where you left off" (the project's three newest tasks, each with an Open button).

The daemon resolves attached projects to their approved folder and folderless projects to
`<daemon data>/project-workspaces/<project UUID>`. The directory is created lazily, is reused by future
tasks and daemon restarts, and never changes the project's public empty `path`. Managed workspaces are
plain folders, so branch isolation is unavailable. Explicit task directories must belong to the selected
project or one of its worktrees; missing attached folders never fall back to a managed directory.
Session `projectId` persists in the existing JSON record and survives restart, hand-off and review.
Removing a project forgets its registry entry but leaves its workspace files and session history on disk.

A headless smoke created a project with an empty folder through `projects.create`, started a
real OMP task by `projectId`, and observed completion with the same persisted project ID.
The isolated daemon shut down afterward; no frontend dev server or visual check was used.

Local new tasks use structured harnesses only (Claude Code, Codex and Oh My Pi), keeping the conversation and
central skills/MCP integration inside Orole; the Home system picker can also launch supported remote process sessions. The model input
uses harness-discovered choices and explicitly sends the discovered default (or first available model),

## Task chat composer

Task chat uses a compact coss InputGroup: a one-line-height textarea, attachment `+`, provider/model
selector, effort label, and round up-arrow Send button share the input. Explicit newlines expand it
up to six rows; ordinary wrapping does not grow the composer. Enter sends; Ctrl+Enter inserts a newline
at the selection. IME composition never sends. Failed sends retain the draft and staged attachments.
The footer shows checkout/branch information, opt-in dictation, and a compact context ring. The coss
context popover uses the AI Elements context layout: measured occupancy, progress, compact token
counts, and separate provider usage counters. Unknown occupancy is never shown as zero; no price or
token-category estimates are invented.

`useTaskMessage` and `TaskMessageControls` reuse homepage model labels, discovered catalogs, attachment
staging, and coss popover/button/slider components. The provider stays fixed to the conversation.
`Session.followup` supplies daemon-derived capabilities. Codex changes model/effort on its existing
thread; OMP acknowledges `set_model`/`set_thinking_level` and verifies their actual state; Claude
acknowledges `set_model`, but exposes effort changes only on ended-session continuation. Unsupported
controls explain why. Empty API settings preserve the current value; explicit selected settings are
captured per queued message. Local structured continuation requires the native session ID and never
falls back to a new conversation. Resuming a stopped session does not release its paused queue.
The existing explicitly labelled remote-process Start task flow still uses `Agents.prompt` without
attachment/configuration controls. There is no separate Resume button or daemon-lifetime footer.
Tasks survive GUI restarts, not daemon exit. Headless interaction coverage exercises sending, retry,
Ctrl+Enter insertion, attachment retention, and model/queue settings; no visual check was run.

Headless titlebar smoke exercised task selection, provider logo rendering, Stop, returning to the dashboard,
switching to Settings without stale task metadata, and opening/closing the Changes sheet with a diff error.
The full frontend check passed; native titlebar geometry and sheet appearance were not visually checked.

## Bot chat view

`features/chat/ChatView.tsx` hosts the `chat` view. It shows, in order: "needs the desktop app" in the browser
preview; the New bot page (`builder/NewBot`, lazy) while `useChat().builder.open`; a setup card linking to
Settings → AI when no provider is connected; load states for the bot list; "Create your first bot" /
"Pick a bot"; otherwise `Conversation` for the selected bot (keyed by bot id, so each bot gets its own runtime
and composer).

The daemon owns every conversation. `stores/chatMessages.ts` is a disposable, event-synchronised window per bot:
the latest page on `load`, older pages on `loadOlder` (`beforeSeq`), `chat.message` events upsert by id (a
streaming snapshot replaces its message in place; `draft:` ids and bots never opened are ignored), reconnect and
window focus refetch the latest page and merge it with what events delivered meanwhile, and stale responses are
dropped by request token. About 300 messages per bot stay in memory unless the reader has paged back. `send`
stores nothing optimistically: it upserts the user message the daemon returns and the reply arrives by event; a
failed send keeps its exact request (same `clientNonce`) so Retry is idempotent. Composer drafts and the
research toggle are kept per bot.

`features/chat/runtime/` adapts that store to assistant-ui (`useExternalStoreRuntime`, no thread list, branching
or editing, because the daemon supports none). `convert.ts` maps daemon messages to `ThreadMessageLike`
(text/reasoning native, tool rows to `tool-call`, citations to `source`, report/delegation/memory/notice to
`data-*` parts; the daemon record rides in `metadata.custom` and is what the renderer draws, so nothing is
lost). `attachments.ts` is the `AttachmentAdapter`: files are validated client-side for UX only (daemon rules
are authoritative; the model's `vision`/`pdf` caps come from the LLM store when known), staged as soon as they
are added via `beginAttachment`/`attachmentChunk` (1 MiB base64 chunks)/`commitAttachment`, shown as
uploading/done/error chips, and discarded on remove. Research mode (offered only with the `research` tool) and
attachments are mutually exclusive, as in the daemon.

`Conversation.tsx` is a `ThreadPrimitive` view: it scrolls back (older pages load near the top without moving
the reader), sticks to the bottom while following a stream, announces "Responding"/"Done" in a polite live
region, and dims queued user messages ("Queued"). `Composer.tsx`: Enter sends, Shift+Enter inserts a newline, IME
composition never sends; Send stays available while a reply runs (the daemon queues the message) next to Stop;
the `+` menu holds Attach files, Research mode, read-only tool chips and Bot settings. There is no @mention picker
(the daemon has no routing for it). `parts/` holds the pure message renderers shared with the bot builder's live
preview (`ChatMessageView`, `MessageParts`), so a preview draws exactly what the conversation draws.

**Title bar, avatars, creation.** In Chat the app title bar (`AppShell`) shows only the selected bot's avatar and
name plus its overflow menu (`features/chat/BotHeader`: Edit, Export, Clear). There is no per-conversation header
and the model slug is not shown in the header or the composer. The bot rail (`components/shell/BotRail`) has one
"Search bots" field with a `+` button beside it; the palette's Ctrl+K button is a Code-mode control and is not
drawn in Chat (the shortcut still works).

Avatars are generated, never chosen: `lib/botAvatar.ts` renders DiceBear's `gaze` style (CC0 1.0, packages
`@dicebear/core` and `@dicebear/styles`) from the seed in `Bot.avatar`, shown through `<img>` so it cannot run
script. A new bot's seed is a short hash of its name (`avatarSeed`), so it fits the daemon's 16-character limit
and stays stable when the bot is renamed. Bots saved before this change keep their old `avatar` text, which is now
just another seed. `Bot.color` is no longer used by the UI (the field is carried through unchanged).

New bot (`builder/NewBot`) asks for a name and a model only and creates the bot with `config.setup = true`; it
then opens the conversation. The daemon makes the bot speak first: `Manager.SaveBot` stores a hidden user message
(a text part with `hidden: true`, read by the model, never drawn or indexed) and runs a turn on it. While `setup`
is set the bot gets two tools (`internal/chat/tools/setup.go`) and a setup section in its system prompt that lists
the user's other bots (fenced data) so it proposes roles nobody fills yet: `ask_user` (a question with 2-6
suggested answers, each a label plus optional description, stored as a `question` part) and `save_profile`
(writes its own description and instructions and clears `setup`). The `question` part renders as
`parts/QuestionCard`: lettered suggestions plus a free-text field, either of which is sent as the user's next
message; it is read-only once the conversation moves on. The rail shows an orange dot on the avatar while the
last message is an unanswered question (`MessagePreview.awaiting`) and a pulsing blue one while a reply runs;
row actions are reached by right-click. Reply placeholders use the assistant-ui typing indicator, and the hover
action row under a reply is always laid out (it fades, never mounts) so showing it cannot shift content.
Everything else lives in the bot settings panel below. There is no separate bot editor page.

**Bot settings panel.** `BotPanel` is a right-hand panel (toggle in the title bar, "Bot settings" in menus) with the
avatar, an editable name and description, and three flat tabs (no cards, little text): Persona (model, reasoning,
Executive assistant switch), Tools (built-in tools, Integrations / MCP servers, skills) and Knowledge (memory scopes
and grants, uploaded documents). One form drives all tabs with a shared Save/Discard bar. Instructions have no
editor: the bot writes them in its setup interview (`save_profile`) and rewrites them with `update_instructions`
(offered to every finished bot, only on the user's request; Persona shows them read-only). Saving keeps `setup`.

Memory writes are always automatic (there is no approval setting; `BotConfig.memoryApproval` is gone, and only
already-pending legacy entries still show an approve/reject list). Only executive assistants (`config.executive`,
ticked on New bot or switched in Persona) get `ask_bot`; they may ask every other active bot, so there is no
per-bot allow-list. Exports never carry the flag, so an imported file cannot grant itself delegation.
